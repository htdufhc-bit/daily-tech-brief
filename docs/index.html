오늘의 기술

REST와 GraphQL

커리큘럼 #9 웹 ⏱ 5분

REST는 자원마다 주소를 두고 HTTP 메서드로 다루는 API 설계 방식이고, GraphQL은 클라이언트가 필요한 데이터의 모양을 쿼리로 직접 지정하는 API 질의 언어다.

왜 필요한가

웹과 모바일 앱이 서버에서 데이터를 받아 오는 방법은 프런트엔드 개발의 기본이다. REST는 단순하고 HTTP의 기능을 그대로 활용하지만, 화면이 복잡해지면 두 가지 불편이 생긴다.

  • 오버페치(over-fetching): 화면에 이름만 필요한데 응답에는 수십 개 필드가 담겨 온다.
  • 언더페치(under-fetching): 화면 하나를 그리려고 /users/1, /users/1/posts처럼 요청을 여러 번 보내야 한다.

특히 모바일 환경에서는 요청 횟수와 전송량이 곧 속도와 데이터 비용이다. GraphQL은 이 문제를 풀려고 Facebook이 만들어 공개한 방식으로, 클라이언트가 응답의 모양을 정하게 한다. 대신 서버 구현이 복잡해지고 캐시가 어려워지는 대가가 따른다.

동작 원리

  1. REST: 자원(resource)마다 주소를 두고 HTTP 메서드로 동작을 나타낸다. GET /users/1은 조회, POST /users는 생성이다. 응답의 모양은 서버가 정한다.
  2. GraphQL: 엔드포인트는 보통 /graphql 하나다. 클라이언트가 필요한 필드를 쿼리 문자열로 적어 POST로 보내면, 서버가 스키마(타입 정의)에 맞춰 그 필드만 담아 응답한다.
  3. 서버는 스키마의 각 필드마다 리졸버(resolver) 함수를 두고, 쿼리가 요청한 필드의 리졸버만 호출해 결과를 조립한다.
  4. REST는 URL과 메서드 단위로 HTTP 캐시(Cache-Control, ETag)를 그대로 쓸 수 있다. GraphQL은 대부분 POST 하나로 오가므로 HTTP 캐시가 잘 맞지 않아 클라이언트 라이브러리나 별도 캐시 계층이 필요하다.
  5. 오류도 다르다. REST는 상태 코드(404, 500 등)로 알리고, GraphQL은 부분 실패가 있어도 보통 200과 함께 본문의 errors 배열로 알린다.

예시

같은 화면(사용자 이름과 최근 글 제목 3개)을 두 방식으로 가져오는 요청이다. REST는 보통 요청이 두 번 필요하고, 각 응답에는 쓰지 않는 필드도 따라온다.

GET /users/1
GET /users/1/posts?limit=3

GraphQL은 한 번의 요청으로 필요한 필드만 골라 받는다.

query {
  user(id: 1) {
    name
    posts(limit: 3) {
      title
    }
  }
}

서버 쪽 스키마는 다음처럼 타입으로 정의한다.

type User {
  id: ID!
  name: String!
  posts(limit: Int): [Post!]!
}
type Post {
  id: ID!
  title: String!
}
type Query {
  user(id: ID!): User
}

언제 쓰고 언제 안 쓰나

REST가 잘 맞는 경우 - 자원 구조가 단순하고 CRUD 중심인 서비스 - HTTP 캐시나 CDN을 적극 활용해야 하는 공개 API - 팀이 작아 스키마와 리졸버 같은 추가 구조를 감당하기 부담스러울 때

GraphQL이 잘 맞는 경우 - 웹, iOS, Android처럼 클라이언트마다 필요한 데이터가 다른 서비스 - 화면 하나가 여러 자원을 조합해야 하는 복잡한 UI - 타입이 있는 스키마로 프런트엔드와 백엔드가 계약을 맺고 싶을 때

피해야 할 경우와 주의점 - 단순한 API에 GraphQL을 도입하면 과설계가 되기 쉽다. - 중첩 쿼리 때문에 데이터베이스 조회가 폭발하는 N+1 문제가 생길 수 있어 DataLoader 같은 배치 도구와 쿼리 깊이 제한이 필요하다. - 둘 중 하나만 고집할 필요는 없다. 한 서비스에서 외부 공개용은 REST, 내부 앱용은 GraphQL로 섞어 쓰기도 한다.

오늘의 기술

HTTPS와 TLS

커리큘럼 #19 네트워크 ⏱ 6분

**HTTPS**는 HTTP 통신을 **TLS**(Transport Layer Security)로 감싸서 도청, 변조, 위장을 막는 프로토콜 조합이다.

왜 필요한가

평문 HTTP는 요청과 응답이 그대로 네트워크를 지나간다. 카페 와이파이나 중간 라우터에서 누구든 로그인 정보와 쿠키를 읽을 수 있고, 내용을 몰래 바꿔 광고나 악성 코드를 끼워 넣을 수도 있다. 접속한 서버가 진짜인지 확인할 방법도 없다.

TLS는 이 세 가지를 한꺼번에 해결한다.

  • 기밀성: 제3자가 내용을 읽지 못하도록 암호화한다.
  • 무결성: 전송 중 내용이 바뀌면 바로 알아챈다.
  • 인증: 서버(필요하면 클라이언트)가 정말 그 주체인지 인증서로 확인한다.

동작 원리

TLS 1.3 기준의 연결 과정은 크게 다음과 같다.

  1. ClientHello: 클라이언트가 지원하는 암호 스위트 목록과 임시 공개키 값(키 교환용), 난수를 보낸다.
  2. ServerHello: 서버가 사용할 암호 스위트를 고르고 자신의 키 교환 값과 난수를 보낸다. 이 시점에 양쪽은 ECDHE 같은 키 교환으로 같은 비밀값을 계산해 낸다.
  3. 인증서 전달: 서버가 인증서와, 자신이 개인키 소유자임을 증명하는 서명을 보낸다. 이후의 메시지는 이미 암호화되어 있다.
  4. 인증서 검증: 클라이언트는 인증서가 신뢰하는 CA(인증 기관)의 서명으로 이어지는지, 도메인 이름이 맞는지, 유효기간이 지나지 않았는지 확인한다.
  5. Finished: 양쪽이 지금까지의 대화 내용을 확인하는 메시지를 교환하면 핸드셰이크가 끝난다.
  6. 데이터 전송: 핸드셰이크에서 만든 대칭키로 AES-GCM 같은 빠른 대칭 암호화를 써서 HTTP 데이터를 주고받는다.

공개키 방식은 느리기 때문에 키를 합의하는 데만 쓰고, 실제 데이터는 대칭키로 암호화한다는 점이 핵심이다. 또한 키 교환에 매 연결마다 새 임시 키를 쓰므로 나중에 서버 개인키가 유출되어도 과거 통신은 풀리지 않는다. 이것을 전방 비밀성(forward secrecy)이라고 한다. TLS 1.3은 핸드셰이크를 1 왕복으로 줄여 TLS 1.2보다 연결이 빠르다.

예시

서버가 어떤 인증서와 프로토콜을 쓰는지는 openssl 명령으로 직접 확인할 수 있다. 아래는 example.com에 접속해 협상된 TLS 버전과 인증서 정보를 보는 예시다.

# TLS 1.3으로 접속해 핸드셰이크 결과 확인
openssl s_client -connect example.com:443 -servername example.com -tls1_3 </dev/null 2>/dev/null \
  | grep -E "Protocol|Cipher|subject=|issuer=|Verification"

# 인증서 유효기간만 보기
openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null \
  | openssl x509 -noout -dates

출력에서 TLSv1.3과 TLS_AES_256_GCM_SHA384 같은 암호 스위트, 그리고 Verification: OK를 확인할 수 있다. 서버 쪽에서는 nginx로 다음처럼 설정해 낡은 버전을 막는다.

server {
    listen 443 ssl;
    server_name example.com;
    ssl_certificate     /etc/ssl/example.com.crt;
    ssl_certificate_key /etc/ssl/example.com.key;
    ssl_protocols TLSv1.2 TLSv1.3;
    add_header Strict-Transport-Security "max-age=31536000" always;
}

언제 쓰고 언제 안 쓰나

쓰면 좋은 경우: 사실상 모든 웹 서비스에 쓴다. 로그인, 결제, API 호출은 물론 정적인 페이지도 변조를 막기 위해 HTTPS를 쓰는 것이 기본이다. 서비스 간 내부 통신에도 mTLS(양방향 인증)를 적용하면 안전하다.

주의할 점:

  • 인증서 만료를 놓치면 서비스가 즉시 접속 불가가 되므로 자동 갱신(예: ACME)을 설정한다.
  • TLS 1.0, 1.1과 SSLv3는 취약하므로 끈다.
  • 개인키는 절대 저장소에 올리지 않는다.
  • HTTPS는 전송 구간만 보호한다. 서버가 해킹되거나 데이터베이스가 유출되는 사고는 막지 못한다.
  • 인증서 검증 오류를 "무시" 옵션으로 넘기는 코드는 TLS의 인증 기능을 통째로 없애므로 운영 환경에서 쓰지 않는다.

오늘의 기술

RAG(검색 증강 생성)

커리큘럼 #14 AI/ML ⏱ 6분

RAG는 질문과 관련된 문서를 먼저 검색한 뒤, 그 내용을 근거로 LLM이 답을 생성하게 하는 기법이다.

왜 필요한가

LLM은 학습이 끝난 시점까지의 지식만 갖고 있고, 모르는 내용도 그럴듯하게 지어내는 환각(hallucination) 문제가 있습니다. 회사 내부 문서나 어제 나온 소식처럼 학습 데이터에 없는 정보는 아예 알지 못합니다.

모델을 새 데이터로 다시 학습(파인튜닝)시키는 방법도 있지만, 비용이 크고 내용이 바뀔 때마다 반복해야 합니다. 또 어떤 문서를 근거로 답했는지 확인하기도 어렵습니다. RAG는 모델은 그대로 두고 필요한 자료를 질문 시점에 건네주는 방식으로 이 불편을 줄입니다. 문서만 갱신하면 답도 최신으로 바뀌고, 답변에 출처를 달 수 있다는 점이 큰 장점입니다.

동작 원리

RAG 시스템은 크게 준비 단계와 질의 단계로 나뉩니다.

준비 단계 (인덱싱)

  1. 문서를 수백 토큰 정도의 청크(chunk) 로 나눕니다. 너무 길면 검색이 흐려지고, 너무 짧으면 맥락이 사라집니다.
  2. 각 청크를 임베딩 모델에 넣어 의미를 담은 숫자 벡터로 바꿉니다. 의미가 비슷한 글은 벡터 공간에서 가까운 위치에 놓입니다.
  3. 벡터와 원문을 벡터 데이터베이스(또는 벡터 검색을 지원하는 DB)에 저장합니다.

질의 단계

  1. 사용자의 질문도 같은 임베딩 모델로 벡터로 바꿉니다.
  2. 저장된 벡터 중 질문과 가장 가까운 상위 k개 청크를 찾습니다. 보통 코사인 유사도를 씁니다.
  3. 찾은 청크를 "아래 자료만 근거로 답하라"는 지시와 함께 프롬프트에 붙입니다.
  4. LLM이 이 프롬프트로 답을 생성하고, 사용한 청크의 출처를 함께 보여 줍니다.

검색 품질이 곧 답변 품질입니다. 키워드 검색(BM25)과 벡터 검색을 섞는 하이브리드 검색이나, 가져온 후보를 다시 정렬하는 리랭커를 더해 정확도를 높이기도 합니다.

예시

아래는 외부 라이브러리 없이 RAG의 뼈대만 보여 주는 파이썬 예시입니다. 실제 서비스에서는 단어 횟수 대신 임베딩 모델을 쓰지만, 흐름은 같습니다. 문서를 벡터로 바꾸고, 질문과 가장 비슷한 문서를 골라, 프롬프트를 조립합니다.

import math
from collections import Counter

docs = [
    "환불은 구매 후 7일 이내에 고객센터에서 신청할 수 있다.",
    "배송은 결제 완료 후 평균 2일이 걸린다.",
    "회원 탈퇴는 설정 메뉴의 계정 항목에서 가능하다.",
]

def embed(text):
    # 데모용 가짜 임베딩: 글자 2개씩 묶은 조각의 개수
    t = text.replace(" ", "")
    return Counter(t[i:i + 2] for i in range(len(t) - 1))

def cosine(a, b):
    dot = sum(a[k] * b[k] for k in a)
    na = math.sqrt(sum(v * v for v in a.values()))
    nb = math.sqrt(sum(v * v for v in b.values()))
    return dot / (na * nb) if na and nb else 0.0

index = [(d, embed(d)) for d in docs]

question = "환불은 언제까지 신청해야 하나요?"
q = embed(question)
top = sorted(index, key=lambda x: cosine(q, x[1]), reverse=True)[:1]

context = "\n".join(d for d, _ in top)
prompt = f"아래 자료만 근거로 답하세요.\n[자료]\n{context}\n\n[질문]\n{question}"
print(prompt)  # 이 프롬프트를 LLM에 보낸다

실행하면 환불 문서가 선택되어 프롬프트에 들어갑니다. 이제 이 프롬프트를 어떤 LLM API에 보내도, 모델은 "7일 이내"라는 근거를 보고 답할 수 있습니다.

언제 쓰고 언제 안 쓰나

쓰면 좋은 경우

  • 사내 문서, 제품 매뉴얼, 법령처럼 모델이 모르는 자료로 질의응답을 만들 때
  • 자주 바뀌는 정보를 다루고 매번 재학습하기 어려울 때
  • 답변에 출처를 달아 사용자가 직접 검증하게 해야 할 때

피해야 할 경우

  • 자료가 짧아서 통째로 프롬프트에 넣어도 충분할 때는 검색 단계가 오히려 복잡도만 늘립니다.
  • 말투나 형식처럼 모델의 행동 방식을 바꾸려는 목적이라면 RAG보다 프롬프트 설계나 파인튜닝이 맞습니다.
  • 접근 권한이 다른 문서를 한 인덱스에 섞으면 권한 없는 사람에게 내용이 새어 나갈 수 있으니 검색 단계에서 권한을 걸러야 합니다.
  • 검색이 엉뚱한 청크를 가져오면 모델이 그 내용을 그대로 믿고 틀린 답을 하므로, 검색 품질을 따로 평가해야 합니다.

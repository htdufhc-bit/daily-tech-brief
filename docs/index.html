오늘의 기술

DNS 동작 방식

커리큘럼 #11 네트워크 ⏱ 6분

DNS(Domain Name System)는 `example.com` 같은 사람이 읽는 도메인 이름을 컴퓨터가 통신에 쓰는 IP 주소로 바꿔 주는 분산 이름 조회 시스템이다.

왜 필요한가

인터넷의 모든 통신은 IP 주소로 이루어지지만, 사람은 93.184.x.x 같은 숫자를 외우기 어렵다. 초기 인터넷에서는 모든 호스트의 이름과 주소를 하나의 hosts 파일에 모아 배포했다. 그러나 호스트가 늘자 파일 하나를 모든 컴퓨터에 최신으로 유지하는 일이 불가능해졌다.

DNS는 이 문제를 계층적으로 위임하는 분산 데이터베이스로 풀었다. 이름 공간을 트리로 나누고 각 구간의 관리를 다른 조직에 맡기면, 중앙에서 전부 관리하지 않아도 되고 서버 하나가 죽어도 전체가 멈추지 않는다. 또 서버 IP가 바뀌어도 이름은 그대로 두고 레코드만 고치면 되므로 서비스를 옮기기 쉽다. DNS가 없다면 사용자는 서비스를 바꿀 때마다 새 주소를 직접 알아야 한다.

동작 원리

  1. 브라우저가 example.com의 IP 주소를 알아내야 한다. 먼저 브라우저 캐시와 운영체제 캐시를 확인하고, 없으면 설정된 재귀 리졸버(보통 ISP나 공용 DNS)에게 묻는다.
  2. 리졸버도 캐시에 답이 없으면 루트 서버에 묻는다. 루트 서버는 답을 직접 주지 않고 .com을 담당하는 TLD 서버 주소를 알려 준다.
  3. 리졸버는 TLD 서버에 example.com을 묻는다. TLD 서버는 해당 도메인의 권한 네임서버 주소를 알려 준다.
  4. 리졸버는 권한 네임서버에 묻고, 여기서 비로소 A(IPv4)나 AAAA(IPv6) 레코드로 된 최종 답을 받는다.
  5. 리졸버는 답을 TTL(Time To Live) 시간 동안 캐시에 저장하고 브라우저에 돌려준다. 같은 이름을 다시 물으면 1~4단계를 건너뛰고 캐시에서 바로 답한다.

이름 공간은 .(루트) → com → example 처럼 오른쪽에서 왼쪽으로 내려가는 트리 구조이고, 각 구간의 관리 책임이 다른 조직에 위임된다. 그래서 전 세계 이름을 한 곳에서 관리하지 않아도 된다.

자주 쓰는 레코드는 다음과 같다.

  • A / AAAA: 이름 → IPv4 / IPv6 주소
  • CNAME: 이름 → 다른 이름(별칭)
  • MX: 도메인의 메일 서버
  • NS: 해당 영역을 담당하는 네임서버
  • TXT: 임의의 텍스트(도메인 소유 증명, SPF 등)

예시

dig 명령으로 위 과정을 직접 눈으로 볼 수 있다. +trace 옵션은 루트 서버부터 시작해 한 단계씩 내려가는 질의를 그대로 보여 준다.

# 일반 질의: 리졸버가 캐시까지 활용해 최종 답만 돌려준다
dig example.com A

# 루트 -> TLD -> 권한 네임서버 순서로 따라가며 출력한다
dig +trace example.com A

# 응답의 TTL(초)을 확인한다. 같은 질의를 반복하면 값이 줄어드는 것을 볼 수 있다
dig +noall +answer example.com A

출력의 ANSWER SECTION에서 example.com. 300 IN A 93.184.x.x 같은 줄을 찾으면 된다. 가운데 숫자가 남은 TTL이고, 마지막이 해석된 IP 주소다. 실제 주소와 값은 시점에 따라 다르다.

파이썬 표준 라이브러리로도 간단히 해석해 볼 수 있다. 이 방식은 운영체제의 리졸버를 거치므로 캐시와 /etc/hosts 설정이 함께 반영된다.

import socket

for family, _, _, _, addr in socket.getaddrinfo("example.com", 443, type=socket.SOCK_STREAM):
    print(family.name, addr[0])

언제 쓰고 언제 안 쓰나

쓰면 좋은 경우

  • 서비스에 고정된 이름을 주고 뒤의 서버는 자유롭게 교체하고 싶을 때. 레코드의 IP만 바꾸면 된다.
  • CNAME으로 CDN이나 클라우드 로드 밸런서를 가리켜 트래픽을 분산하고 싶을 때.
  • TXT 레코드로 도메인 소유를 증명하거나 메일 인증(SPF, DKIM)을 설정할 때.

주의할 점

  • TTL을 길게 잡으면 캐시 덕에 빠르고 부하가 적지만, 주소를 바꿔도 전파되는 데 오래 걸린다. 이전 작업 전에는 TTL을 미리 낮춰 두는 것이 좋다.
  • 기본 DNS는 암호화와 서명이 없어 응답이 위조될 수 있다. 민감한 환경에서는 DNSSEC이나 DoH/DoT 같은 보호 수단을 고려해야 한다.
  • 장애 원인이 DNS인데 서버 문제로 오해하는 경우가 많다. 접속이 안 될 때는 dig로 이름 해석부터 확인하는 습관을 들이자.

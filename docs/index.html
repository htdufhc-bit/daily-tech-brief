오늘의 기술

JWT

커리큘럼 #15 보안 ⏱ 6분

**JWT(JSON Web Token)**는 사용자 정보와 권한 같은 주장(claim)을 JSON으로 담고 서명을 붙여, 서버가 상태를 저장하지 않고도 검증할 수 있게 한 토큰 형식이다 (RFC 7519).

왜 필요한가

전통적인 로그인은 서버가 세션 ID를 만들어 메모리나 DB에 저장하고, 요청마다 그 ID로 사용자를 찾아 보는 세션 방식이다. 서버가 한 대일 때는 단순하지만, 서버가 여러 대로 늘면 세션 저장소를 공유해야 하고 요청마다 조회 비용이 든다.

JWT는 "누구인지"를 토큰 자체에 담고 서명으로 위조를 막는다. 어느 서버든 비밀 키(또는 공개 키)만 있으면 저장소 조회 없이 토큰을 검증할 수 있어, 서버를 수평 확장하거나 여러 서비스가 같은 로그인 정보를 공유하기 쉽다.

동작 원리

JWT는 점(.)으로 이어진 세 부분으로 이루어진다: header.payload.signature. 각 부분은 Base64URL로 인코딩된다.

  1. Header: 서명 알고리즘과 토큰 종류를 적는다. 예: {"alg":"HS256","typ":"JWT"}
  2. Payload: 클레임을 담는다. sub(사용자 식별자), iat(발급 시각), exp(만료 시각) 같은 표준 클레임과 role 같은 사용자 정의 클레임이 있다.
  3. Signature: Base64URL(header) + "." + Base64URL(payload)를 비밀 키로 서명한 값이다. HS256은 대칭 키 HMAC, RS256은 개인 키로 서명하고 공개 키로 검증한다.
  4. 로그인에 성공하면 서버가 JWT를 발급하고, 클라이언트는 이후 요청의 Authorization: Bearer <토큰> 헤더에 담아 보낸다.
  5. 서버는 서명을 다시 계산해 일치하는지, exp가 지나지 않았는지 확인한 뒤 payload를 신뢰한다.

중요한 점은 payload가 암호화가 아니라 인코딩일 뿐이라는 것이다. 누구나 디코딩해 내용을 읽을 수 있고, 서명은 "변조되지 않았음"만 보장한다. 그래서 비밀번호 같은 민감 정보는 넣지 않는다.

예시

Python의 PyJWT 라이브러리로 토큰을 발급하고 검증하는 예시다. 만료 시간을 15분으로 두고, 검증할 때 허용할 알고리즘을 반드시 명시한다.

import datetime as dt
import jwt  # pip install PyJWT

SECRET = "change-me-to-a-long-random-secret"

def issue_token(user_id: str) -> str:
    now = dt.datetime.now(dt.timezone.utc)
    payload = {"sub": user_id, "iat": now, "exp": now + dt.timedelta(minutes=15)}
    return jwt.encode(payload, SECRET, algorithm="HS256")

def verify_token(token: str) -> str:
    # algorithms를 지정하지 않으면 공격자가 alg를 바꿔 검증을 우회할 수 있다
    claims = jwt.decode(token, SECRET, algorithms=["HS256"])
    return claims["sub"]

token = issue_token("user-42")
print(verify_token(token))  # user-42

jwt.decode는 서명이 틀리거나 exp가 지났으면 예외를 던지므로, 호출하는 쪽에서 jwt.InvalidTokenError를 잡아 401 응답으로 바꾸면 된다.

언제 쓰고 언제 안 쓰나

쓰면 좋은 경우 - 여러 서버·마이크로서비스가 세션 저장소 없이 같은 인증 정보를 검증해야 할 때 - 짧은 수명의 접근 토큰이 필요한 API, 모바일 앱, 서비스 간 호출 - OAuth 2.0 / OpenID Connect에서 ID 토큰 형태로 쓸 때

피해야 할 경우 - 발급한 토큰을 즉시 폐기해야 하는 요구가 강할 때. 서명 방식은 만료 전까지 유효하므로, 폐기하려면 결국 블랙리스트 같은 서버 상태가 필요하다. - 토큰에 민감한 정보를 담으려 할 때. payload는 누구나 읽을 수 있다. - 단순한 단일 서버 웹사이트. 서버 세션과 쿠키가 더 단순하고 안전한 경우가 많다.

실무 팁: 접근 토큰은 짧게(수 분~수십 분) 유지하고 긴 수명의 리프레시 토큰을 따로 두며, 브라우저에서는 HttpOnly 쿠키에 담아 XSS로 탈취되는 위험을 줄인다. 서명 알고리즘은 항상 서버에서 고정하고, alg: none 토큰은 거부한다.

오늘의 기술

가상 메모리

커리큘럼 #12 운영체제 ⏱ 6분

가상 메모리는 프로세스마다 독립된 연속 주소 공간을 보여 주고, 운영체제가 이를 실제 물리 메모리(와 디스크)에 필요할 때 연결해 주는 메모리 관리 기법입니다.

왜 필요한가

초기 컴퓨터에서는 프로그램이 물리 주소를 직접 썼습니다. 그러면 다음과 같은 불편이 생깁니다.

  • 한 프로그램이 다른 프로그램의 메모리를 실수로(혹은 악의적으로) 덮어쓸 수 있습니다.
  • 프로그램을 어느 주소에 올릴지 미리 정해야 해서, 같은 프로그램을 여러 개 띄우기 어렵습니다.
  • 물리 메모리보다 큰 프로그램은 아예 실행할 수 없습니다.

가상 메모리는 "모든 프로세스가 자기만의 넓은 메모리를 가진 것처럼" 보이게 해 이 문제를 한 번에 풀었습니다. 격리(보호), 단순한 프로그래밍 모델, 물리 메모리보다 큰 작업 실행이 모두 여기서 나옵니다.

동작 원리

  1. 프로세스가 쓰는 주소는 가상 주소입니다. 주소 공간은 보통 4KB 크기의 페이지로 나뉩니다.
  2. 물리 메모리도 같은 크기의 프레임으로 나뉘고, 운영체제가 프로세스마다 페이지 테이블(가상 페이지 → 물리 프레임)을 유지합니다.
  3. CPU의 MMU가 메모리를 접근할 때마다 페이지 테이블로 가상 주소를 물리 주소로 번역합니다. 번역 결과는 TLB라는 작은 캐시에 저장해 속도를 높입니다.
  4. 페이지 테이블 항목에는 "메모리에 있음" 비트와 읽기/쓰기/실행 권한이 있습니다. 없는 페이지나 권한 없는 접근은 페이지 폴트라는 예외로 운영체제에 넘어갑니다.
  5. 운영체제는 폴트 원인에 따라 처리합니다. 아직 올리지 않은 페이지면 디스크에서 읽어 프레임에 채우고(요구 페이징), 정말 잘못된 접근이면 프로세스에 SIGSEGV를 보냅니다.
  6. 프레임이 부족하면 잘 안 쓰는 페이지를 디스크(스왑)로 내보내고(페이지 교체, 예: LRU 근사) 그 프레임을 재사용합니다.

덕분에 fork() 직후 부모와 자식이 같은 프레임을 읽기 전용으로 공유하다가, 쓰기가 생길 때만 복사하는 Copy-on-Write 같은 최적화도 가능합니다.

예시

Linux에서 파일을 mmap으로 매핑하면 가상 주소만 먼저 잡히고, 실제 물리 메모리는 접근하는 순간 페이지 폴트로 채워지는 것을 볼 수 있습니다. 아래 코드는 1GB 크기의 파일을 매핑한 뒤 일부만 읽고, 프로세스의 가상 크기(VmSize)와 실제 상주 크기(VmRSS)를 비교합니다.

import mmap, os

def mem():
    with open("/proc/self/status") as f:
        return {l.split(":")[0]: l.split(":")[1].strip()
                for l in f if l.startswith(("VmSize", "VmRSS"))}

path = "/tmp/big.bin"
with open(path, "wb") as f:
    f.truncate(1 << 30)          # 1GB 희소 파일

f = open(path, "r+b")
m = mmap.mmap(f.fileno(), 0)     # 가상 주소 공간만 예약
print("매핑 직후:", mem())

for i in range(0, 100 * 4096, 4096):
    m[i]                         # 100개 페이지 접근 -> 페이지 폴트
print("100페이지 접근 후:", mem())
os.remove(path)

실행하면 VmSize는 매핑 직후부터 약 1GB 커져 있지만 VmRSS는 접근한 페이지만큼(약 400KB)만 늘어납니다. 가상 크기와 실제 사용량이 다르다는 점이 핵심입니다.

언제 쓰고 언제 안 쓰나

알아두면 좋은 경우 - 메모리 사용량을 볼 때 top의 VIRT(가상)와 RES(상주)를 구분해야 할 때 - 대용량 파일을 mmap으로 다루거나, 프로세스 간 메모리를 공유할 때 - 갑자기 느려졌을 때 스와핑(thrashing)이나 페이지 폴트 급증을 의심해야 할 때

주의할 점 - 가상 메모리는 공짜가 아닙니다. 번역과 페이지 폴트에 비용이 들어서, 작업 집합이 물리 메모리보다 커져 스왑이 계속 일어나면 성능이 급락합니다. - 지연 시간이 중요한 시스템에서는 페이지를 미리 메모리에 고정(mlock)하거나 큰 페이지(huge page)를 써서 TLB 미스를 줄이기도 합니다. - 가상 주소가 크다고 해서 그만큼 메모리를 쓰는 것은 아니므로, 단순히 VIRT 수치만 보고 누수라고 판단하지 않아야 합니다.

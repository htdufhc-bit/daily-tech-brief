오늘의 기술

CI/CD 파이프라인

커리큘럼 #21 클라우드/인프라 ⏱ 4분

**CI/CD**는 코드 변경을 자동으로 빌드·테스트해 합치고(CI), 검증된 결과물을 자동으로 배포 가능한 상태로 만들거나 실제로 배포하는(CD) 일련의 자동화 절차다.

왜 필요한가

여러 사람이 각자 오래 작업한 코드를 한꺼번에 합치면 충돌이 쌓이고, 어디서 깨졌는지 찾기 어렵다. 배포를 사람이 손으로 하면 빠뜨린 단계, 환경 차이, 새벽 배포 같은 사고가 생긴다.

CI/CD는 변경을 작게, 자주 합치고 매번 같은 절차로 자동 검증해서 이 문제를 풀려고 나왔다. 문제를 일찍 발견할수록 고치는 비용이 작아지고, 배포가 따분한 일상이 되면 위험도 줄어든다.

동작 원리

  1. 개발자가 브랜치에서 작업하고 저장소에 푸시하거나 풀 리퀘스트를 연다.
  2. 저장소에 설정된 트리거(푸시, PR, 일정 등)가 파이프라인을 깨운다.
  3. CI 단계: 깨끗한 실행 환경(러너)에서 코드를 받아 의존성을 설치하고, 빌드, 린트, 단위·통합 테스트를 순서대로 돌린다. 하나라도 실패하면 파이프라인이 멈추고 개발자에게 알린다.
  4. 산출물(컨테이너 이미지, 패키지 등)을 만들어 버전을 붙여 저장한다.
  5. CD 단계: 산출물을 스테이징 환경에 배포해 확인한다. 연속 제공(Continuous Delivery)은 운영 배포 직전에 사람의 승인을 두고, 연속 배포(Continuous Deployment)는 승인 없이 운영까지 자동으로 보낸다.
  6. 배포 뒤 모니터링으로 이상이 보이면 이전 버전으로 롤백한다.

예시

GitHub Actions로 푸시와 PR마다 Node.js 프로젝트를 테스트하는 최소 설정이다. .github/workflows/ci.yml에 저장하면 동작한다.

name: CI
on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - run: npm test

on이 트리거, jobs가 작업 단위, steps가 순서대로 실행되는 단계다. 테스트가 실패하면 PR에 빨간 표시가 뜨므로 병합 전에 문제를 알 수 있다.

언제 쓰고 언제 안 쓰나

쓰면 좋은 경우: 팀으로 개발하거나, 테스트가 있거나, 배포를 자주 하는 프로젝트. 혼자 하는 작은 프로젝트도 테스트와 린트를 자동화하면 이득이 크다.

피해야 할 경우·주의점: 테스트가 거의 없는데 자동 배포부터 붙이면 버그가 그대로 운영에 나간다. 파이프라인이 너무 느리면 아무도 기다리지 않게 되므로 캐시와 병렬 실행으로 줄여야 한다. 비밀 값(API 키 등)은 코드에 쓰지 말고 저장소의 시크릿 기능으로 주입한다. 불안정한 테스트(flaky test)는 방치하지 말고 바로 고친다.

오늘의 기술

로드 밸런서

커리큘럼 #27 네트워크 ⏱ 5분

로드 밸런서는 들어오는 요청을 여러 서버에 나누어 전달해 부하를 분산하고, 장애 난 서버를 자동으로 우회하게 해 주는 장치(또는 소프트웨어)입니다.

왜 필요한가

서버 한 대로 서비스를 운영하면 두 가지 문제가 생깁니다. 첫째, 접속자가 늘어 그 서버의 CPU나 메모리가 한계에 닿으면 응답이 느려지거나 멈춥니다. 둘째, 그 서버가 고장 나면 서비스 전체가 중단되는 단일 장애점(SPOF) 이 됩니다.

서버를 여러 대 두면 두 문제를 모두 줄일 수 있지만, 이번에는 "사용자가 어느 서버로 가야 하는가"라는 문제가 생깁니다. 로드 밸런서는 이 선택을 대신해 주는 장치입니다. 사용자는 주소 하나만 알면 되고, 운영자는 사용자 모르게 서버를 추가하거나 빼고 점검할 수 있습니다.

동작 원리

  1. 클라이언트가 서비스 주소(예: example.com)로 요청을 보내면 DNS가 로드 밸런서의 주소를 알려 줍니다.
  2. 로드 밸런서가 요청을 받고, 등록된 서버 목록 중 상태가 정상인 서버만 후보로 남깁니다.
  3. 정해진 분배 알고리즘으로 그중 한 대를 고릅니다. 대표적인 방식은 다음과 같습니다.
  4. 라운드 로빈: 서버를 순서대로 돌아가며 배정합니다. 가장 단순합니다.
  5. 최소 연결(Least Connections): 현재 처리 중인 연결이 가장 적은 서버를 고릅니다. 요청마다 처리 시간이 다를 때 유리합니다.
  6. IP 해시: 클라이언트 IP로 서버를 정해 같은 사용자가 같은 서버에 가게 합니다.
  7. 선택한 서버로 요청을 전달하고, 서버의 응답을 클라이언트에 돌려줍니다.
  8. 로드 밸런서는 주기적으로 헬스 체크(예: /health 요청)를 보내 응답이 없는 서버를 목록에서 빼고, 복구되면 다시 넣습니다.

동작하는 계층에 따라 L4와 L7으로 나눕니다. L4는 IP와 포트 정보만 보고 빠르게 넘기고, L7은 HTTP 헤더·경로·쿠키까지 읽어서 /api는 A 서버군, /images는 B 서버군처럼 내용 기반으로 나눌 수 있습니다.

예시

Nginx로 서버 세 대에 요청을 나누는 가장 기본적인 설정입니다. upstream 블록에 서버를 등록하고, proxy_pass로 그쪽에 요청을 넘깁니다.

upstream backend {
    least_conn;                      # 최소 연결 방식 (생략하면 라운드 로빈)
    server 10.0.0.11:8080;
    server 10.0.0.12:8080;
    server 10.0.0.13:8080 backup;    # 다른 서버가 모두 죽었을 때만 사용
}

server {
    listen 80;
    location / {
        proxy_pass http://backend;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}

X-Real-IP 헤더를 붙이면 백엔드 서버가 로드 밸런서가 아니라 실제 사용자 IP를 알 수 있습니다. 설정을 바꾼 뒤에는 nginx -t로 문법을 확인하고 nginx -s reload로 적용합니다.

언제 쓰고 언제 안 쓰나

쓰면 좋은 경우 - 트래픽이 한 서버의 처리 한계를 넘을 때(수평 확장) - 배포나 점검 중에도 서비스를 멈추고 싶지 않을 때(서버를 하나씩 빼고 교체) - 장애가 난 서버를 자동으로 우회해야 할 때

피해야 하거나 주의할 경우 - 트래픽이 적은 개인 프로젝트에는 오히려 구성만 복잡해집니다. - 로그인 정보를 서버 메모리에 저장하는 세션 방식이면 요청마다 서버가 바뀔 때 로그아웃되는 문제가 생깁니다. 세션을 Redis 같은 공유 저장소로 옮기거나 고정 세션(sticky session)을 써야 합니다. - 로드 밸런서 자체가 SPOF가 될 수 있으니, 실서비스에서는 로드 밸런서도 이중화하거나 클라우드의 관리형 서비스를 씁니다.

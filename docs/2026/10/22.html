오늘의 기술

Use-After-Free와 메모리 안전성

트렌드 픽 보안 ⏱ 6분

**Use-After-Free(UAF)**는 이미 해제한 메모리를 프로그램이 계속 사용해서 데이터 손상이나 임의 코드 실행으로 이어지는 메모리 안전성 취약점이다.

왜 필요한가

C/C++ 같은 언어는 개발자가 malloc/free로 메모리의 수명을 직접 관리한다. 속도와 제어력은 얻지만 "누가 언제 해제하는가"를 사람이 정확히 기억해야 한다는 부담이 생긴다.

이 약속이 한 번이라도 어긋나면 프로그램은 이미 다른 용도로 쓰이는 메모리를 건드리게 된다. 업계 보고서들은 대형 소프트웨어 보안 취약점의 상당수가 이런 메모리 안전성 문제라고 지적해 왔다.

오늘 뉴스의 PHP 취약점 두 건이 좋은 예다. 하나는 메모리 한도(memory_limit)에 걸렸을 때 반쯤 초기화된 내부 데이터가 남아 메모리가 손상되는 문제이고, 다른 하나는 치명적 오류 뒤 내부 상태가 이전 요청의 메모리를 가리켜 UAF가 생기는 문제다. 둘 다 웹 서버가 요청을 처리하는 아주 이른 단계에서 일어나서 영향이 크다.

동작 원리

  1. 프로그램이 malloc 같은 함수로 힙에서 메모리 블록을 할당받고 포인터로 가리킨다.
  2. 작업이 끝나면 free로 블록을 반환한다. 이때 블록은 할당자의 "빈 목록"에 들어가지만, 기존 포인터 값은 그대로 남는다(댕글링 포인터).
  3. 다음 malloc 요청이 오면 할당자는 방금 반환된 블록을 재사용하는 경우가 많다. 같은 주소가 전혀 다른 객체의 것이 된다.
  4. 코드가 옛 포인터를 계속 쓰면, 새 객체의 데이터를 옛 객체인 줄 알고 읽거나 쓴다. 이것이 Use-After-Free다.
  5. 공격자는 요청 내용을 조절해 해제된 자리에 자신이 만든 데이터(예: 함수 포인터)를 채워 넣는다. 옛 포인터로 그 값을 호출하게 되면 공격자가 고른 주소로 실행 흐름이 넘어간다.
  6. 이렇게 임의 코드 실행(RCE)까지 이어질 수 있다. 서버가 인증 전 요청을 처리하는 구간에서 생기면 로그인 없이도 공격이 가능하다.

메모리 부족(OOM) 상황도 비슷한 경로를 만든다. 할당이 실패해 초기화가 반쯤 끝난 구조체가 남았는데 이후 코드가 정상 값이라 믿고 쓰면 메모리가 손상된다.

예시

C로 쓴 아주 작은 Use-After-Free 예시다. 해제된 a의 자리를 b가 재사용하는 모습을 확인할 수 있다. (실제 동작은 할당자에 따라 다를 수 있고, 학습 목적으로만 실행하자.)

#include <stdio.h>
#include <stdlib.h>
#include <string.h>

int main(void) {
    char *a = malloc(16);
    strcpy(a, "user-data");
    free(a);                 // a는 해제됐지만 값은 그대로 남는다

    char *b = malloc(16);    // 같은 크기 → 같은 주소를 재사용할 가능성이 높다
    strcpy(b, "attacker-data");

    printf("a=%p b=%p\n", (void *)a, (void *)b);
    printf("a가 가리키는 값: %s\n", a);   // UAF: "attacker-data"가 출력될 수 있다
    return 0;
}

다음은 AddressSanitizer로 같은 코드를 잡아내는 명령이다. 컴파일 옵션만 바꾸면 해제된 메모리에 접근하는 순간 오류 보고서와 함께 프로그램이 멈춘다.

gcc -fsanitize=address -g uaf.c -o uaf && ./uaf

언제 쓰고 언제 안 쓰나

알아 두면 좋은 경우: C/C++로 서버, 파서, 네트워크 코드를 만들거나 읽을 때, 그리고 PHP·Python 같은 언어의 확장 모듈과 런타임을 운영할 때다. 이런 런타임은 안쪽이 C로 되어 있어 같은 종류의 버그가 생길 수 있다.

대응 방법 - 보안 패치가 나오면 지체하지 말고 업데이트한다. 이번 PHP 사례처럼 인증 전에 공격할 수 있는 취약점은 시간이 곧 위험이다. - 새 코드는 Rust처럼 컴파일러가 소유권을 검사하는 언어를 고려한다. C/C++에서는 스마트 포인터를 쓰고, 테스트와 CI에서 AddressSanitizer와 퍼징을 돌린다. - free 직후 포인터를 NULL로 바꾸는 습관은 도움이 되지만, 같은 포인터의 복사본까지 막아 주지는 못한다.

피해야 할 생각: "내 코드는 PHP/Python이라 메모리 버그와 무관하다"는 판단이다. 언어 런타임의 버그는 응용 코드로는 고칠 수 없으므로 버전 관리가 유일한 방어선이다.

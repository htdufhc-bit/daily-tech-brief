오늘의 기술

가비지 컬렉션

커리큘럼 #16 언어/도구 ⏱ 5분

**가비지 컬렉션(GC)**은 프로그램이 더는 사용하지 않는 메모리를 런타임이 자동으로 찾아 회수하는 기법이다.

왜 필요한가

C처럼 메모리를 직접 관리하면 malloc과 free의 짝을 개발자가 맞춰야 한다. 해제를 빠뜨리면 메모리 누수가 쌓이고, 이미 해제한 메모리를 다시 쓰면 댕글링 포인터와 이중 해제 같은 버그, 나아가 보안 취약점으로 이어진다. 이런 오류는 찾기 어렵고 프로그램 규모가 커질수록 사람이 일일이 추적하기 힘들다.

GC는 "언제 해제할지"의 판단을 런타임에 맡겨 이 부담을 덜어 준다. 개발자는 비즈니스 로직에 집중할 수 있고 메모리 관련 버그의 큰 부류가 사라진다. 대신 GC 자체가 CPU와 시간을 쓰고, 해제 시점을 정확히 예측하기 어렵다는 비용이 생긴다.

동작 원리

  1. 할당: 프로그램이 객체를 만들면 런타임이 힙 메모리에서 공간을 내어 준다.
  2. 도달 가능성 판단: 스택 변수, 전역 변수, 레지스터 같은 루트에서 출발해 참조를 따라갈 수 있는 객체는 "살아 있다"고 본다. 어디서도 닿을 수 없는 객체가 쓰레기다.
  3. 회수: 쓰레기 객체의 공간을 비워 다음 할당에 재사용한다.

대표적인 방식은 세 가지다.

  • 참조 카운팅: 객체마다 자신을 가리키는 참조 수를 센다. 0이 되면 즉시 해제한다. 단순하고 즉각적이지만 서로를 가리키는 순환 참조는 카운트가 0이 되지 않아 따로 처리가 필요하다. CPython이 이 방식에 순환 탐지용 가비지 컬렉터를 덧붙여 쓴다.
  • 마크 앤 스윕: 루트에서 출발해 도달 가능한 객체에 표시(mark)하고, 힙 전체를 훑어 표시 없는 객체를 청소(sweep)한다. 순환 참조도 문제없지만 수행 중 프로그램이 멈추는 stop-the-world 시간이 생길 수 있다.
  • 세대별(generational) 수집: "대부분의 객체는 금방 죽는다"는 관찰에 기대어 힙을 젊은 세대와 늙은 세대로 나누고, 젊은 세대를 자주·가볍게 수집한다. JVM 등이 쓴다.

현대 런타임은 이 방식들을 섞고, 멈춤 시간을 줄이기 위해 수집 작업을 프로그램과 동시에(concurrent) 수행하는 기법도 쓴다.

예시

파이썬에서 순환 참조가 어떻게 회수되는지 직접 확인해 보자. 두 객체가 서로를 가리키면 참조 카운트만으로는 해제되지 않아 순환 탐지 수집기가 필요하다.

import gc

class Node:
    def __init__(self, name):
        self.name = name
        self.other = None

    def __del__(self):
        print(f"{self.name} 해제됨")

a = Node("A")
b = Node("B")
a.other = b
b.other = a      # 순환 참조

del a, b         # 참조 카운트가 0이 되지 않아 아직 해제되지 않음
print("del 이후")
print("수집된 객체 수:", gc.collect())   # 순환 수집기가 A, B를 회수

del 직후에는 아무것도 출력되지 않고, gc.collect()를 호출했을 때 비로소 "A 해제됨", "B 해제됨"이 출력된다. 이렇게 참조 카운팅만으로 회수되지 않는 쓰레기를 별도의 수집기가 찾아낸다는 점을 보여 준다.

언제 쓰고 언제 안 쓰나

쓰면 좋은 경우: 웹 서비스, 업무 시스템, 스크립트처럼 개발 생산성과 안전성이 중요하고 수십 밀리초 단위의 가끔 생기는 멈춤을 감당할 수 있는 곳. Java, Go, Python, JavaScript, C# 같은 언어 대부분이 GC를 기본으로 제공한다.

주의하거나 피해야 할 경우: 지연 시간이 엄격한 실시간 시스템, 임베디드, 게임 엔진의 프레임 루프, 메모리가 매우 제한된 환경. 이런 곳에서는 수동 관리나 Rust의 소유권 모델처럼 GC 없는 방식이 더 적합할 수 있다. GC가 있어도 불필요하게 객체를 오래 붙잡아 두면(캐시나 리스너 미해제 등) 누수가 생기므로, 힙 사용량과 GC 로그를 주기적으로 확인하는 습관이 필요하다.

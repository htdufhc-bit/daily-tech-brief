오늘의 기술

CORS

커리큘럼 #17 웹 ⏱ 7분

CORS(교차 출처 리소스 공유)는 한 출처의 웹 페이지가 다른 출처의 리소스를 요청할 수 있도록, 서버가 HTTP 헤더로 브라우저에 허용 여부를 알리는 규약이다.

왜 필요한가

웹 브라우저는 보안을 위해 동일 출처 정책(Same-Origin Policy)을 적용한다. 출처는 프로토콜·호스트·포트의 조합인데, 이 중 하나라도 다르면 다른 출처로 본다. 이 정책이 없다면 사용자가 로그인한 은행 사이트의 쿠키를 악성 페이지의 스크립트가 그대로 이용해 응답을 읽어 갈 수 있다.

그런데 요즘은 프론트엔드(app.example.com)와 API 서버(api.example.com)를 따로 두는 구조가 흔하다. 동일 출처 정책만 있으면 이런 정상적인 호출까지 막힌다. CORS는 서버가 직접 "이 출처는 믿는다"고 선언하게 해서, 보안은 유지하면서 필요한 교차 출처 통신만 열어 주는 방법이다. CORS가 없다면 JSONP 같은 우회 기법에 의존해야 하고, 이는 훨씬 위험하다.

동작 원리

  1. 브라우저가 다른 출처(https://app.example)의 API(https://api.example)로 요청을 보낼 때, 요청에 Origin: https://app.example 헤더를 자동으로 붙인다.
  2. 서버는 응답에 Access-Control-Allow-Origin 헤더를 넣어 이 출처를 허용할지 알린다.
  3. 브라우저는 응답 헤더를 확인해 허용되지 않았으면 JavaScript가 응답을 읽지 못하게 막고 콘솔에 CORS 오류를 낸다. 요청 자체는 서버에 도착했을 수 있다.
  4. GET/POST(단순 형식)가 아니거나 Authorization, Content-Type: application/json 같은 헤더를 쓰는 요청은 프리플라이트를 거친다. 브라우저가 먼저 OPTIONS 요청으로 Access-Control-Request-Method와 Access-Control-Request-Headers를 보내 허용 여부를 묻는다.
  5. 서버가 Access-Control-Allow-Methods, Access-Control-Allow-Headers로 답하고 통과하면, 브라우저가 본 요청을 보낸다. Access-Control-Max-Age로 프리플라이트 결과를 일정 시간 캐시할 수 있다.
  6. 쿠키 같은 자격 증명을 함께 보내려면 클라이언트에서 credentials: "include"를 쓰고, 서버는 Access-Control-Allow-Credentials: true와 구체적인 출처를 돌려줘야 한다. 이때 *는 쓸 수 없다.

예시

프론트엔드(http://localhost:3000)에서 API 서버(http://localhost:8000)를 호출하는 상황이다. 아래는 Python Flask로 만든 서버에서 허용할 출처를 직접 확인해 헤더를 붙이는 예시다.

from flask import Flask, request, make_response

app = Flask(__name__)
ALLOWED = {"http://localhost:3000"}

@app.after_request
def add_cors(resp):
    origin = request.headers.get("Origin")
    if origin in ALLOWED:
        resp.headers["Access-Control-Allow-Origin"] = origin
        resp.headers["Vary"] = "Origin"
        resp.headers["Access-Control-Allow-Headers"] = "Content-Type, Authorization"
        resp.headers["Access-Control-Allow-Methods"] = "GET, POST, PUT, DELETE"
    return resp

@app.route("/api/items", methods=["GET", "POST", "OPTIONS"])
def items():
    if request.method == "OPTIONS":
        return make_response("", 204)
    return {"items": [1, 2, 3]}

프론트엔드에서는 평소처럼 fetch("http://localhost:8000/api/items")를 호출하면 된다. 허용 목록에 없는 출처에서 호출하면 서버는 응답하지만 브라우저가 결과를 JavaScript에 넘기지 않는다. 출처마다 응답이 달라지므로 Vary: Origin을 함께 보내 캐시가 섞이지 않게 한다.

언제 쓰고 언제 안 쓰나

쓰면 좋은 경우

  • 프론트엔드와 API 서버가 서로 다른 도메인·포트에 배포될 때
  • 외부 개발자나 다른 서비스가 브라우저에서 우리 공개 API를 호출해야 할 때
  • 개발 중 localhost:3000과 localhost:8000처럼 포트가 다른 서버를 연결할 때

피해야 할 경우와 주의점

  • 인증이 필요한 API에 Access-Control-Allow-Origin: *를 쓰지 않는다. 요청의 Origin을 검사하지 않고 그대로 되돌려 주는 것도 사실상 모든 출처를 허용하는 위험한 설정이다.
  • CORS는 브라우저가 지키는 규칙이다. curl이나 서버 간 호출은 영향을 받지 않으므로, CORS를 인증·권한 검사의 대체물로 생각하면 안 된다.
  • 가능하면 같은 출처로 맞추는 방법(리버스 프록시로 /api 경로를 묶기)이 설정도 단순하고 프리플라이트 비용도 없다.
  • CORS 오류가 났을 때 서버 로그와 네트워크 탭의 OPTIONS 응답 상태 코드와 헤더를 먼저 확인한다.

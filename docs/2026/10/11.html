오늘의 기술

데이터베이스 인덱스와 B-Tree

커리큘럼 #2 데이터베이스 ⏱ 5분

인덱스는 테이블의 특정 컬럼 값을 정렬해 별도로 저장해 두어, 전체 행을 읽지 않고도 원하는 행을 빨리 찾게 해 주는 자료구조이며, 대부분의 관계형 DB는 이를 B-Tree로 구현한다.

왜 필요한가

테이블에서 조건에 맞는 행을 찾으려면 인덱스가 없을 때 처음부터 끝까지 모든 행을 읽어야 한다(풀 스캔). 책 한 권을 찾으려고 도서관의 모든 책을 한 권씩 꺼내 보는 셈이다. 데이터가 수백만 건으로 늘면 한 번의 조회가 수 초씩 걸려 서비스 전체가 느려진다.

인덱스는 책 뒤의 색인과 같다. 값을 미리 정렬해 두고 위치를 기록해 두면, 전체를 읽지 않고도 원하는 행으로 바로 찾아갈 수 있다. 그 대가로 저장 공간과 쓰기 시 추가 작업이 든다는 점은 기억해야 한다.

동작 원리

  1. 인덱스를 만들면 DB는 지정한 컬럼 값을 정렬된 상태로 따로 저장하고, 각 값에 실제 행의 위치(포인터)를 붙여 둔다.
  2. 이 정렬 구조가 보통 B-Tree다. 루트 노드 하나에서 시작해 중간 노드를 거쳐 맨 아래 리프 노드에 도달하는 균형 잡힌 트리이며, 모든 리프는 같은 깊이에 있다.
  3. 조회할 때는 루트에서 "찾는 값이 어느 범위에 속하는가"를 비교하며 내려간다. 노드 하나에 수백 개의 키가 들어가므로 깊이는 보통 3~4단계에 불과하다. 수백만 건이라도 디스크를 몇 번만 읽으면 된다. 시간 복잡도는 O(log N)이다.
  4. 리프 노드끼리는 연결 리스트로 이어져 있어 BETWEEN, ORDER BY 같은 범위 검색도 빠르다.
  5. 데이터를 삽입·수정·삭제하면 인덱스도 함께 갱신해야 한다. 노드가 가득 차면 둘로 쪼개고(split), 트리의 균형은 계속 유지된다.

예시

주문 테이블에서 특정 고객의 주문을 찾는 상황이다. 인덱스가 없으면 DB는 모든 행을 읽는 풀 스캔을 한다. 먼저 인덱스를 만들고 EXPLAIN으로 실행 계획이 어떻게 바뀌는지 확인한다.

CREATE TABLE orders (
  id          BIGSERIAL PRIMARY KEY,
  customer_id BIGINT NOT NULL,
  created_at  TIMESTAMP NOT NULL
);

-- 인덱스 생성 전: Seq Scan (전체 행을 훑는다)
EXPLAIN SELECT * FROM orders WHERE customer_id = 42;

CREATE INDEX idx_orders_customer ON orders (customer_id);

-- 생성 후: Index Scan using idx_orders_customer
EXPLAIN SELECT * FROM orders WHERE customer_id = 42;

-- 복합 인덱스는 왼쪽 컬럼부터 순서대로 활용된다
CREATE INDEX idx_orders_customer_created ON orders (customer_id, created_at);

복합 인덱스 (customer_id, created_at)는 customer_id만으로 검색하거나 두 컬럼을 함께 검색할 때는 쓰이지만, created_at만으로 검색할 때는 일반적으로 쓰이지 않는다. 이를 최좌측 접두사 규칙이라 부른다.

언제 쓰고 언제 안 쓰나

쓰면 좋은 경우 - WHERE, JOIN, ORDER BY에 자주 쓰이는 컬럼 - 값의 종류가 많은(카디널리티가 높은) 컬럼. 예: 사용자 ID, 이메일 - 읽기가 쓰기보다 훨씬 많은 테이블

피해야 할 경우 - 행이 몇백 건뿐인 작은 테이블. 풀 스캔이 더 빠를 수 있다. - 성별처럼 값의 종류가 적은 컬럼. 걸러지는 행이 거의 없다. - 쓰기가 매우 잦은 테이블에 인덱스를 무작정 늘리는 경우. 쓸 때마다 모든 인덱스를 갱신해야 해서 느려지고 저장 공간도 더 든다. - WHERE LOWER(email) = ...처럼 컬럼에 함수를 적용하면 일반 인덱스를 타지 못한다. 이때는 함수 기반 인덱스가 필요하다.

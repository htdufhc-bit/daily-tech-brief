오늘의 기술

NoSQL의 종류

커리큘럼 #18 데이터베이스 ⏱ 5분

NoSQL은 관계형 테이블 모델 대신 키-값, 문서, 와이드 컬럼, 그래프 같은 다양한 데이터 모델로 데이터를 저장하는 데이터베이스를 통칭하는 말이다.

왜 필요한가

관계형 데이터베이스(RDBMS)는 정해진 스키마와 조인, 강한 트랜잭션에 강하지만, 서비스가 커지면 불편한 점이 생긴다. 데이터 구조가 자주 바뀌면 스키마를 고치기 부담스럽고, 트래픽이 폭증하면 서버 한 대의 성능을 올리는 수직 확장에는 한계가 있다. 또 SNS의 친구 관계처럼 연결 자체가 중요한 데이터는 조인을 여러 번 겹쳐야 해서 느려진다. NoSQL은 이런 문제를 "용도에 맞는 데이터 모델"과 "여러 서버로 나눠 저장하는 수평 확장"으로 풀려고 나왔다. 하나의 만능 DB를 쓰는 대신 문제에 맞는 DB를 고르는 접근이다.

동작 원리

  1. 키-값(Key-Value): 키 하나로 값 하나를 찾는다. 구조가 가장 단순해 매우 빠르며 세션, 캐시, 순위표에 쓴다. 예: Redis, DynamoDB.
  2. 문서(Document): JSON 비슷한 문서를 통째로 저장한다. 문서마다 필드가 달라도 되고, 중첩된 데이터를 한 번에 읽을 수 있다. 예: MongoDB, Couchbase.
  3. 와이드 컬럼(Wide-column): 행 키와 컬럼 패밀리로 데이터를 나눠 여러 서버에 분산 저장한다. 쓰기가 많은 대규모 로그·시계열에 강하다. 예: Cassandra, HBase.
  4. 그래프(Graph): 노드(점)와 엣지(관계)로 저장하고 관계를 따라가며 질의한다. 친구의 친구 찾기, 추천, 사기 탐지처럼 연결이 핵심일 때 쓴다. 예: Neo4j.

공통점은 스키마가 유연하고 수평 확장(서버를 늘리는 방식)을 염두에 두고 설계됐다는 점이다. 대신 많은 NoSQL은 조인과 강한 트랜잭션을 제한적으로 지원하며, 일관성을 조금 양보해 가용성과 속도를 얻는 최종적 일관성(eventual consistency) 모델을 택하는 경우가 많다. 이는 CAP 정리에서 "네트워크 분할 시 일관성과 가용성 중 무엇을 우선할지"의 선택과 이어진다.

예시

문서형 DB인 MongoDB에서 주문과 상품 목록을 한 문서에 담아 저장하고 조회하는 예시다. 관계형이었다면 orders와 order_items 두 테이블을 조인해야 하지만, 여기서는 한 번에 읽는다.

// 주문 하나를 문서로 저장 (items 배열이 문서 안에 중첩됨)
db.orders.insertOne({
  user: "kim",
  status: "paid",
  items: [
    { sku: "A-100", name: "키보드", qty: 1, price: 59000 },
    { sku: "B-200", name: "마우스", qty: 2, price: 25000 }
  ]
});

// 결제 완료된 kim의 주문 조회 (조인 없이 items까지 함께 반환)
db.orders.find({ user: "kim", status: "paid" });

위 코드에서 items의 구조를 주문마다 다르게 해도 오류가 나지 않는다. 이런 유연함이 장점이지만, 필드 이름 오타 같은 실수를 DB가 잡아 주지 않으므로 애플리케이션에서 검증해야 한다.

언제 쓰고 언제 안 쓰나

쓰면 좋은 경우 - 세션, 캐시, 실시간 순위처럼 단순한 조회를 아주 빠르게 해야 할 때 (키-값) - 상품 정보처럼 항목마다 속성이 다르고 구조가 자주 바뀔 때 (문서) - 로그, 센서 데이터처럼 쓰기가 폭발적으로 많고 여러 서버에 분산해야 할 때 (와이드 컬럼) - 추천, 관계 분석처럼 연결을 따라가는 질의가 핵심일 때 (그래프)

피해야 할 경우 - 돈 이체처럼 여러 데이터를 한꺼번에 정확히 갱신해야 하는 강한 트랜잭션이 핵심일 때 - 다양한 조건으로 데이터를 자유롭게 조인·집계해야 할 때 - 데이터가 작고 구조가 안정적이라면 관계형 DB로도 충분하다. 유행 때문에 고르지 말고 접근 패턴을 먼저 정리한 뒤 선택하자.

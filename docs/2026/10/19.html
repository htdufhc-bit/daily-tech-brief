오늘의 기술

트랜잭션 격리 수준

커리큘럼 #10 데이터베이스 ⏱ 6분

트랜잭션 격리 수준은 동시에 실행되는 여러 트랜잭션이 서로의 중간 상태를 얼마나 볼 수 있는지 정하는 규칙으로, 정합성과 성능 사이의 균형을 조절하는 설정이다.

왜 필요한가

은행 앱에서 두 사람이 같은 계좌를 동시에 건드린다고 생각해 보자. 아무 규칙이 없으면 다른 사람이 아직 확정하지 않은 값을 읽어 계산하거나, 내가 확인한 잔액이 바로 다음 순간 바뀌어 있는 일이 생긴다. 그렇다고 모든 트랜잭션을 한 줄로 세워 하나씩 실행하면 안전하지만 너무 느리다. 격리 수준은 "어떤 이상 현상까지 허용하고 그 대신 속도를 얻을 것인가"를 고르게 해 주는 장치다. SQL 표준은 허용 가능한 이상 현상에 따라 네 단계를 정의한다.

동작 원리

  1. 트랜잭션 시작: 두 트랜잭션 A, B가 같은 데이터를 동시에 읽고 쓴다고 하자.
  2. READ UNCOMMITTED: 커밋되지 않은 변경도 읽힌다. 이 경우 더티 리드가 생긴다. A가 값을 바꾸고 롤백했는데 B가 그 값을 이미 읽었다면 B는 존재한 적 없는 데이터를 본 셈이다.
  3. READ COMMITTED: 커밋된 데이터만 읽는다. 더티 리드는 사라지지만, 같은 트랜잭션 안에서 같은 행을 두 번 읽을 때 중간에 다른 트랜잭션이 커밋하면 값이 달라진다(non-repeatable read). PostgreSQL과 Oracle의 기본값이다.
  4. REPEATABLE READ: 트랜잭션이 시작된 시점의 스냅숏을 계속 본다. 같은 행은 항상 같은 값으로 읽힌다. MySQL InnoDB의 기본값이며, 조건에 맞는 행이 새로 생기는 팬텀 리드는 DBMS마다 막는 정도가 다르다.
  5. SERIALIZABLE: 트랜잭션을 마치 한 줄로 차례대로 실행한 것과 같은 결과를 보장한다. 가장 안전하지만 락 대기나 재시도(직렬화 실패)가 늘어 처리량이 떨어진다.

현대 DBMS는 대부분 MVCC(다중 버전 동시성 제어)로 이를 구현한다. 행의 이전 버전을 보관해 두고, 읽는 쪽에는 격리 수준에 맞는 버전을 보여 주므로 읽기가 쓰기를 막지 않는다.

정리하면 아래 표와 같다.

격리 수준 더티 리드 non-repeatable read 팬텀 리드
READ UNCOMMITTED 발생 발생 발생
READ COMMITTED 방지 발생 발생
REPEATABLE READ 방지 방지 표준상 발생(구현마다 다름)
SERIALIZABLE 방지 방지 방지

예시

계좌 이체처럼 읽은 값을 바탕으로 쓰는 작업에서 격리 수준이 어떻게 영향을 주는지 PostgreSQL 문법으로 보자. 아래는 한 세션의 트랜잭션이다. 다른 세션이 중간에 같은 행을 바꾸고 커밋하는 상황을 가정한다.

-- 세션 A
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM accounts WHERE id = 1;   -- 1000

-- (세션 B가 이 사이에 balance를 500으로 바꾸고 COMMIT)

SELECT balance FROM accounts WHERE id = 1;   -- 여전히 1000
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
-- PostgreSQL은 여기서 "could not serialize access due to concurrent update"
-- 오류를 낸다. 애플리케이션이 트랜잭션을 처음부터 재시도해야 한다.
COMMIT;

READ COMMITTED였다면 두 번째 SELECT가 500을 돌려주었을 것이다. 위 예처럼 높은 격리 수준에서는 충돌이 오류로 드러나므로, 재시도 로직을 함께 짜는 것이 중요하다.

언제 쓰고 언제 안 쓰나

기본값(READ COMMITTED)으로 충분한 경우: 단순 조회나 한 번의 UPDATE로 끝나는 일반 웹 요청. 같은 행을 두 번 읽고 비교하는 로직이 없다면 대부분 문제가 없다.

높은 격리 수준이 필요한 경우: 잔액 확인 후 차감, 재고 확인 후 주문처럼 읽은 값에 근거해 쓰는 작업, 같은 시점의 일관된 데이터가 필요한 보고서나 정산 배치. 이때는 REPEATABLE READ나 SERIALIZABLE을 쓰거나, SELECT ... FOR UPDATE로 행을 직접 잠그는 방법도 있다.

피해야 할 경우: 이유 없이 모든 트랜잭션에 SERIALIZABLE을 거는 것. 락 경합과 재시도가 늘어 성능이 떨어진다. 또 같은 이름의 수준이라도 DBMS마다 동작이 다르므로(예: InnoDB의 REPEATABLE READ는 갭 락으로 팬텀을 상당 부분 막는다) 사용하는 DBMS의 문서를 꼭 확인해야 한다.

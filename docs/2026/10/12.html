오늘의 기술

TCP 3-way 핸드셰이크

커리큘럼 #3 네트워크 ⏱ 5분

TCP 3-way 핸드셰이크는 데이터를 보내기 전에 SYN, SYN-ACK, ACK 세 번의 메시지를 교환해 양쪽이 연결 상태와 순서 번호를 합의하는 절차다.

왜 필요한가

IP는 패킷이 도착하는지, 순서가 맞는지 보장하지 않는다. TCP는 그 위에서 신뢰할 수 있는 바이트 스트림을 제공해야 하므로, 데이터를 보내기 전에 두 가지를 먼저 확인해야 한다.

첫째, 상대가 실제로 살아 있고 연결을 받을 준비가 되어 있는가. 둘째, 각 방향에서 몇 번 바이트부터 보낼지(순서 번호)에 대한 합의다. 순서 번호가 없으면 중복·유실·순서 뒤바뀜을 감지할 수 없다. 핸드셰이크가 없다면 오래전에 지연된 패킷을 새 연결의 데이터로 착각하거나, 아무도 듣지 않는 곳에 데이터를 계속 보내게 된다.

동작 원리

  1. SYN: 클라이언트가 임의의 초기 순서 번호(ISN) x를 담은 SYN 세그먼트를 보내고 SYN-SENT 상태가 된다.
  2. SYN-ACK: 서버는 자신의 초기 순서 번호 y를 정하고, 클라이언트의 x를 확인하는 ACK(x+1)를 함께 보낸 뒤 SYN-RECEIVED 상태가 된다.
  3. ACK: 클라이언트가 y+1을 확인하는 ACK를 보내면 양쪽 모두 ESTABLISHED 상태가 되어 데이터를 주고받을 수 있다.

이 과정에서 양쪽이 서로의 순서 번호를 알게 되고, 각자의 송신·수신이 가능함도 확인된다. 서버가 3번째 ACK를 받기 전까지는 연결을 완전히 열지 않기 때문에, 이미 지나간 오래된 SYN이 뒤늦게 도착해도 클라이언트가 응답하지 않으면 연결이 만들어지지 않는다.

연결을 끊을 때는 보통 FIN과 ACK를 양쪽이 각각 주고받는 4-way 과정을 쓴다. 한쪽이 FIN을 보내도 상대는 아직 보낼 데이터가 남았을 수 있어서, 방향별로 따로 닫기 때문이다.

예시

소켓 API에서는 핸드셰이크를 직접 쓰지 않는다. 서버의 listen과 클라이언트의 connect를 호출하면 운영체제 커널이 3단계를 처리한다. 아래는 파이썬으로 TCP 연결을 만드는 최소 예시다.

import socket

# 서버: listen 상태에서 대기 (커널이 SYN을 받아 SYN-ACK를 돌려준다)
srv = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
srv.bind(("127.0.0.1", 9000))
srv.listen()

# 클라이언트: connect가 반환되면 3-way 핸드셰이크가 끝난 것이다
cli = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
cli.connect(("127.0.0.1", 9000))

conn, addr = srv.accept()   # 완료된 연결을 꺼낸다
print("연결됨:", addr)

connect가 성공하면 이미 핸드셰이크가 끝났다는 점을 기억하자. 실제 패킷은 sudo tcpdump -i lo port 9000으로 관찰할 수 있고, 플래그가 [S], [S.], [.] 순서로 나타난다.

언제 쓰고 언제 안 쓰나

알아 두면 좋은 경우: 웹 서버 응답이 느릴 때 연결 지연이 얼마나 되는지 따져 볼 때다. 핸드셰이크는 왕복 1회(1 RTT)가 걸리므로, 먼 서버일수록 첫 요청 전 대기가 커진다. 이런 경우 HTTP Keep-Alive나 커넥션 풀로 연결을 재사용하면 비용을 줄일 수 있다.

주의할 경우: 서버가 SYN만 받고 끝내는 SYN Flood 공격에서는 반쯤 열린 연결이 쌓여 자원이 고갈된다. SYN 쿠키나 백로그 조정으로 대응한다. 또 짧은 요청을 매번 새 연결로 보내는 구조는 지연과 서버 부담이 크다. 지연에 민감하고 손실을 어느 정도 감수할 수 있다면 UDP나 QUIC도 검토할 만하다.

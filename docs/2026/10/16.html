오늘의 기술

OAuth 2.0과 OIDC

커리큘럼 #7 보안 ⏱ 6분

**OAuth 2.0**은 사용자의 비밀번호를 넘기지 않고 다른 앱에 제한된 접근 권한(인가)을 위임하는 표준이고, **OIDC(OpenID Connect)**는 그 위에 "이 사용자가 누구인가"라는 로그인(인증) 정보를 얹은 계층이다.

왜 필요한가

예전에는 외부 서비스가 내 구글 연락처를 읽으려면 구글 비밀번호를 직접 받아야 했다. 그러면 앱이 계정 전체를 쥐게 되고, 앱 하나가 뚫리면 비밀번호가 새며, 권한만 일부 거두는 것도 불가능하다. OAuth는 비밀번호 대신 범위(scope)와 유효 시간이 제한된 토큰을 발급해 이 문제를 풀었다. 다만 OAuth는 "무엇을 할 수 있는가"만 다루고 "누구인가"는 표준이 없어서, 서비스마다 제각각 로그인을 구현하다 보안 사고가 났다. OIDC는 이 빈틈을 표준화한 것이다.

먼저 네 가지 역할을 알아 두자. 리소스 소유자는 사용자, 클라이언트는 접근하려는 앱, 인가 서버는 로그인과 토큰 발급을 맡는 서버, 리소스 서버는 실제 데이터를 가진 API다.

동작 원리

  1. 클라이언트(앱)가 사용자를 인가 서버의 로그인 화면으로 보낸다. 이때 client_id, redirect_uri, scope, state, PKCE용 code_challenge를 쿼리로 전달한다.
  2. 사용자가 인가 서버에서 로그인하고 "이 앱에 이 권한을 줄까요?"라는 동의 화면에서 허용한다.
  3. 인가 서버는 브라우저를 redirect_uri로 되돌리며 일회용 인가 코드를 붙여 준다. state가 처음 보낸 값과 같은지 반드시 확인한다.
  4. 클라이언트는 서버 쪽에서 인가 코드와 code_verifier를 토큰 엔드포인트로 보내 액세스 토큰으로 교환한다. 토큰은 브라우저 주소창에 노출되지 않는다.
  5. 클라이언트는 액세스 토큰을 Authorization: Bearer ... 헤더에 넣어 리소스 서버(API)를 호출한다.
  6. 스코프에 openid가 있으면 토큰 응답에 ID 토큰(JWT)도 온다. 서명, iss(발급자), aud(대상 앱), exp(만료), nonce를 검증한 뒤에야 사용자가 누구인지 믿을 수 있다.

OAuth 2.0에서 액세스 토큰은 클라이언트에게 "내용을 알 수 없는 열쇠"로 취급되고, OIDC의 ID 토큰은 클라이언트가 직접 읽는 "신분 증명서"라는 점이 다르다.

예시

인가 코드 흐름의 첫 요청(로그인 화면으로 보내는 주소)과, 코드를 토큰으로 바꾸는 요청 예시다. 값은 설명용 가짜 값이다.

GET /authorize?response_type=code
  &client_id=my-app
  &redirect_uri=https%3A%2F%2Fapp.example.com%2Fcallback
  &scope=openid%20profile%20email
  &state=xyz123
  &code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
  &code_challenge_method=S256 HTTP/1.1
Host: auth.example.com

사용자가 동의하면 https://app.example.com/callback?code=abc&state=xyz123으로 돌아온다. 이제 서버에서 다음 요청으로 토큰을 받는다.

curl -X POST https://auth.example.com/token \
  -d grant_type=authorization_code \
  -d code=abc \
  -d redirect_uri=https://app.example.com/callback \
  -d client_id=my-app \
  -d code_verifier=원래_만든_랜덤_문자열

응답에는 access_token, expires_in, 그리고 openid 스코프를 요청했다면 id_token이 들어 있다.

언제 쓰고 언제 안 쓰나

쓰면 좋은 경우 - "구글/GitHub/카카오로 로그인"처럼 외부 계정으로 가입·로그인을 받을 때(OIDC) - 서드파티 앱에 내 데이터 일부만 읽기·쓰기 권한을 줄 때(OAuth) - 여러 서비스가 하나의 로그인(SSO)을 공유할 때

피해야 할 경우와 주의점 - 액세스 토큰을 "로그인 증명"으로 쓰지 않는다. 사용자 식별은 검증한 ID 토큰으로 한다. - 모바일·SPA 같은 공개 클라이언트는 비밀키를 숨길 수 없으므로 반드시 PKCE를 쓴다. - 토큰을 localStorage처럼 스크립트가 읽을 수 있는 곳에 오래 보관하지 않고, redirect_uri는 정확히 일치하는 값만 허용한다. - 단순한 내부 서비스 하나의 로그인이라면 OAuth 서버를 직접 만들기보다 검증된 라이브러리나 IdP를 쓰는 편이 안전하다.

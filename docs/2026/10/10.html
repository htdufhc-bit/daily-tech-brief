오늘의 기술

HTTP 캐싱

커리큘럼 #1 웹 ⏱ 7분

**HTTP 캐싱**은 서버의 응답을 브라우저나 중간 서버(CDN, 프록시)에 저장해 두었다가, 같은 요청이 오면 원 서버에 가지 않고 재사용하는 기법이다.

왜 필요한가

웹 페이지 하나를 열 때 HTML, CSS, JS, 이미지 등 수십 개의 요청이 오간다. 매번 서버까지 왕복하면 지연 시간이 늘고, 서버와 네트워크 비용도 커진다. 이미 받은 파일이 바뀌지 않았다면 다시 받을 이유가 없다.

캐싱이 없다면 사용자는 같은 로고 이미지를 페이지를 이동할 때마다 다시 내려받아야 하고, 트래픽이 몰리는 순간 서버는 똑같은 응답을 반복해서 만들어 내느라 한계에 다다른다. HTTP 캐싱은 "언제까지 다시 쓰고, 만료 후에는 어떻게 확인할지"를 헤더로 약속해 이 낭비를 줄인다.

동작 원리

HTTP 캐싱은 크게 신선도(freshness) 검사와 재검증(validation) 두 단계로 동작한다.

  1. 브라우저가 처음 자원을 요청하면 서버가 응답과 함께 Cache-Control: max-age=3600 같은 헤더, 그리고 ETag(내용의 지문) 또는 Last-Modified(마지막 수정 시각)를 보낸다.
  2. 브라우저는 응답을 캐시에 저장한다. max-age 동안은 신선하다고 보고, 네트워크 요청 없이 저장본을 바로 쓴다.
  3. 유효기간이 지나면 저장본은 stale(오래됨) 상태가 된다. 이때 바로 버리지 않고 If-None-Match: "<ETag 값>" 헤더를 붙여 서버에 "내가 가진 버전이 아직 유효한가?"라고 묻는다.
  4. 내용이 그대로면 서버는 본문 없이 304 Not Modified만 돌려준다. 브라우저는 저장본의 유효기간을 갱신해 계속 쓴다. 바뀌었다면 200 OK와 새 본문을 보낸다.

주요 Cache-Control 지시어는 다음과 같다.

  • max-age=N: N초 동안 신선하다.
  • no-cache: 저장은 하되 쓰기 전에 반드시 재검증한다. ("캐시 안 함"이 아니다.)
  • no-store: 어디에도 저장하지 않는다. 민감한 정보에 쓴다.
  • public / private: CDN 같은 공유 캐시에 저장해도 되는지, 개인 브라우저에만 저장할지 정한다.
  • immutable: 유효기간 안에는 절대 바뀌지 않는다고 알려 재검증을 막는다.

예시

정적 파일은 파일명에 해시를 넣고 오래 캐시하고, HTML은 항상 재검증하게 하는 것이 흔한 구성이다. 아래는 Python 표준 라이브러리만으로 만든 작은 서버로, ETag를 비교해 304를 돌려준다.

from http.server import BaseHTTPRequestHandler, HTTPServer
import hashlib

BODY = "안녕하세요, 캐시 예제입니다.".encode("utf-8")
ETAG = '"' + hashlib.md5(BODY).hexdigest() + '"'

class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        if self.headers.get("If-None-Match") == ETAG:
            self.send_response(304)          # 본문 없이 "그대로 써도 된다"
            self.send_header("ETag", ETAG)
            self.end_headers()
            return
        self.send_response(200)
        self.send_header("Content-Type", "text/plain; charset=utf-8")
        self.send_header("Cache-Control", "max-age=60")  # 60초간 신선
        self.send_header("ETag", ETAG)
        self.end_headers()
        self.wfile.write(BODY)

HTTPServer(("127.0.0.1", 8000), Handler).serve_forever()

서버를 실행한 뒤 터미널에서 두 번 요청해 보면 차이가 보인다.

curl -i http://127.0.0.1:8000/
curl -i -H 'If-None-Match: "<위 응답의 ETag 값>"' http://127.0.0.1:8000/

첫 번째는 200과 본문을, 두 번째는 본문 없는 304 Not Modified를 받는다. 브라우저는 이 과정을 자동으로 해 준다.

언제 쓰고 언제 안 쓰나

쓰면 좋은 경우

  • 해시가 붙은 JS/CSS/이미지처럼 내용이 바뀌면 주소도 바뀌는 정적 자원: max-age=31536000, immutable처럼 길게 잡는다.
  • 자주 바뀌지 않는 공개 API 응답이나 CDN 뒤의 콘텐츠: public과 적당한 max-age로 서버 부하를 줄인다.
  • HTML처럼 자주 바뀌는 문서: no-cache와 ETag로 매번 가볍게 재검증한다.

피해야 할 경우

  • 개인 정보, 결제, 인증 토큰이 담긴 응답을 공유 캐시가 저장하게 두면 다른 사람에게 노출될 수 있다. private이나 no-store를 쓴다.
  • 파일명이 고정된 자원에 긴 max-age를 주면, 배포 후에도 사용자가 옛 버전을 오래 보게 된다.
  • 캐시를 무효화하는 방법(주소 변경 등)을 정하지 않은 채 유효기간만 길게 잡지 않는다.

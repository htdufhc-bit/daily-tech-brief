오늘의 기술

CSR, SSR, SSG

커리큘럼 #25 웹 ⏱ 6분

CSR, SSR, SSG는 웹 페이지의 HTML을 **언제, 어디서** 만들지에 따른 세 가지 렌더링 방식으로, 각각 브라우저에서, 요청 시 서버에서, 빌드 시점에 만드는 것을 뜻한다.

왜 필요한가

초기 웹은 서버가 매번 완성된 HTML을 보내 주는 구조였다. 그러다 사용자 경험이 중요해지면서 페이지 이동 때마다 화면이 깜빡이지 않는 단일 페이지 애플리케이션(SPA)이 널리 쓰였고, 이는 브라우저에서 화면을 그리는 CSR 방식이다.

CSR은 부드럽지만 약점이 있다. JS를 모두 내려받아 실행하기 전까지 빈 화면이 보이고, 처음 받는 HTML에 내용이 없어 검색 엔진이나 링크 미리보기가 내용을 읽기 어렵다. 이 불편을 줄이려고 서버에서 먼저 HTML을 만들어 주는 SSR, 아예 미리 만들어 두는 SSG가 다시 주목받았다.

결국 세 방식은 첫 화면 속도, 검색 노출, 최신성, 서버 비용 사이에서 무엇을 우선할지에 대한 서로 다른 답이다.

동작 원리

CSR (Client-Side Rendering)

  1. 서버는 거의 비어 있는 HTML과 큰 JavaScript 번들을 보낸다.
  2. 브라우저가 JS를 내려받아 실행한다.
  3. JS가 API를 호출해 데이터를 받고, DOM을 만들어 화면을 그린다.
  4. 이후 페이지 이동은 서버에 HTML을 다시 요청하지 않고 JS가 화면만 바꾼다.

SSR (Server-Side Rendering)

  1. 브라우저가 페이지를 요청하면 서버가 그 자리에서 데이터를 조회해 HTML을 완성한다.
  2. 완성된 HTML이 도착하자마자 화면에 보인다.
  3. 이어서 JS가 내려와 이벤트를 연결한다. 이 과정을 하이드레이션(hydration)이라 한다.
  4. 요청마다 서버가 일하므로 최신 데이터를 보여줄 수 있지만 서버 부하가 늘어난다.

SSG (Static Site Generation)

  1. 배포(빌드) 시점에 모든 페이지의 HTML을 미리 만들어 파일로 저장한다.
  2. 요청이 오면 서버는 계산 없이 완성된 파일을 그대로 내려준다.
  3. CDN에 올려 두면 전 세계에서 매우 빠르게 응답한다.
  4. 내용이 바뀌면 다시 빌드해야 한다. 일부 프레임워크는 일정 시간마다 특정 페이지만 다시 만드는 증분 재생성(ISR)을 제공한다.

예시

아래는 Next.js 예시다. 같은 fetch라도 캐시 옵션에 따라 SSG처럼, 혹은 SSR처럼 동작한다.

// app/posts/page.js — SSG에 가까운 동작: 빌드 시 한 번 만들어 재사용
export default async function Posts() {
  const res = await fetch("https://example.com/api/posts", { cache: "force-cache" });
  const posts = await res.json();
  return <ul>{posts.map(p => <li key={p.id}>{p.title}</li>)}</ul>;
}

// app/me/page.js — SSR 동작: 요청마다 서버에서 새로 렌더링
export default async function Me() {
  const res = await fetch("https://example.com/api/me", { cache: "no-store" });
  const me = await res.json();
  return <h1>{me.name}님 안녕하세요</h1>;
}

첫 번째 페이지는 내용이 모든 방문자에게 같으므로 미리 만들어 두고, 두 번째 페이지는 사용자마다 달라서 요청 때마다 서버가 그려 준다. CSR은 서버가 빈 껍데기 HTML만 주고 브라우저에서 useEffect 등으로 데이터를 불러와 화면을 채우는 방식이다.

언제 쓰고 언제 안 쓰나

CSR이 어울리는 경우 - 로그인 후 사용하는 대시보드, 관리자 도구처럼 검색 노출이 필요 없고 상호작용이 많은 화면 - 피해야 할 경우: 첫 화면 속도와 검색 노출이 중요한 공개 페이지

SSR이 어울리는 경우 - 사용자마다 내용이 다르거나 자주 바뀌면서도 검색 노출이 필요한 페이지(상품 상세, 피드 등) - 피해야 할 경우: 트래픽이 많은데 내용은 거의 변하지 않는 페이지. 매 요청마다 서버가 일하므로 비용이 낭비된다.

SSG가 어울리는 경우 - 블로그, 문서, 랜딩 페이지처럼 내용이 모든 방문자에게 같고 자주 바뀌지 않는 페이지 - 피해야 할 경우: 페이지 수가 매우 많거나 내용이 수시로 바뀌는 서비스. 빌드 시간이 길어지고 최신성이 떨어진다.

실제 서비스는 한 가지만 쓰지 않는다. 한 사이트 안에서도 소개 페이지는 SSG, 상품 목록은 SSR, 마이페이지는 CSR처럼 페이지 단위로 섞어 쓰는 것이 일반적이다. 선택이 막막하다면 "이 페이지의 내용이 누구에게나 같은가, 얼마나 자주 바뀌는가, 검색에 노출돼야 하는가" 세 가지 질문부터 던져 보자.

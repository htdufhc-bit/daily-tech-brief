오늘의 기술

임베딩과 벡터 DB

커리큘럼 #22 AI/ML ⏱ 6분

**임베딩**은 텍스트·이미지 같은 데이터를 의미가 담긴 숫자 벡터로 바꾼 것이고, **벡터 DB**는 이 벡터를 저장하고 '가장 비슷한 것'을 빠르게 찾아 주는 데이터베이스다.

왜 필요한가

기존 키워드 검색은 글자가 같아야 찾는다. "노트북 배터리가 빨리 닳아요"를 검색해도 "랩톱 전력 소모 문제"라고 쓴 문서는 놓친다. 동의어, 표현 차이, 다른 언어까지 사람이 일일이 규칙으로 처리하기는 불가능하다.

임베딩은 의미가 비슷하면 숫자도 비슷해지도록 모델이 미리 학습해 이 문제를 푼다. 그러면 검색은 "벡터 사이의 거리 계산"이라는 수학 문제가 된다. 다만 벡터가 수백만 개로 늘면 일반 DB의 B-Tree 인덱스로는 거리 기준 검색을 할 수 없다. 고차원 벡터에 맞는 인덱스와 저장 방식이 필요해서 벡터 DB가 등장했다.

LLM 시대에는 쓰임이 더 커졌다. 모델이 모르는 사내 문서나 최신 정보를 검색해 프롬프트에 붙여 주는 RAG의 검색 단계를 벡터 DB가 맡는다.

동작 원리

  1. 임베딩 생성: 텍스트를 임베딩 모델에 넣으면 [0.12, -0.53, ...]처럼 수백~수천 개 숫자로 된 벡터가 나온다. 의미가 비슷한 문장은 벡터 공간에서 가까운 곳에 놓이도록 모델이 학습되어 있다.
  2. 저장: 문서를 적당한 길이로 나눠(청킹) 각각 임베딩을 만들고, 원문·메타데이터와 함께 벡터 DB에 저장한다.
  3. 질의: 검색어도 같은 모델로 벡터로 바꾼다. 서로 다른 모델의 벡터는 비교할 수 없으므로 반드시 같은 모델을 써야 한다.
  4. 유사도 계산: 두 벡터가 얼마나 가까운지 코사인 유사도(방향이 비슷한 정도), 내적, 유클리드 거리 같은 척도로 잰다.
  5. 근사 최근접 탐색(ANN): 벡터가 수백만 개면 전부 비교하기 어렵다. 그래서 HNSW(여러 층의 그래프를 따라 이웃을 찾아가는 방식)나 IVF(벡터를 군집으로 나눠 가까운 군집만 뒤지는 방식) 같은 인덱스로 정확도를 조금 양보하고 속도를 크게 높인다.
  6. 결과 활용: 가까운 상위 k개를 돌려받아 그대로 보여 주거나, LLM에게 근거 문서로 넘겨 답을 만들게 한다(RAG).

예시

PostgreSQL의 pgvector 확장을 쓰면 기존 DB에서도 벡터 검색을 해 볼 수 있다. 아래는 3차원짜리 장난감 벡터로 만든 예시이고, 실제 임베딩은 보통 384~3072차원이다.

CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE docs (
  id        bigserial PRIMARY KEY,
  content   text,
  embedding vector(3)
);

INSERT INTO docs (content, embedding) VALUES
  ('고양이는 귀엽다', '[0.9, 0.1, 0.0]'),
  ('강아지는 충성스럽다', '[0.8, 0.2, 0.1]'),
  ('주식 시장이 하락했다', '[0.0, 0.1, 0.9]');

-- HNSW 인덱스 (코사인 거리)
CREATE INDEX ON docs USING hnsw (embedding vector_cosine_ops);

-- 질의 벡터와 가장 가까운 2건
SELECT content, embedding <=> '[0.85, 0.15, 0.05]' AS distance
FROM docs
ORDER BY distance
LIMIT 2;

<=>는 코사인 거리 연산자이고 값이 작을수록 비슷하다. 결과로는 동물에 관한 두 문장이 나오고 주식 문장은 멀리 떨어진다. 키워드가 하나도 겹치지 않아도 의미로 찾는다는 점이 핵심이다.

언제 쓰고 언제 안 쓰나

쓰면 좋은 경우

  • 의미 기반 문서 검색, FAQ 챗봇, 사내 지식 검색(RAG)
  • 비슷한 상품·기사·이미지 추천, 중복 문서 탐지
  • 키워드가 정확히 맞지 않는 자연어 질의가 많은 서비스

피해야 할 경우

  • 주문번호, 이름, 날짜 범위처럼 정확히 일치해야 하는 조회: 일반 DB의 인덱스가 더 정확하고 싸다.
  • 데이터가 수천 건 이하인 경우: 전체를 그냥 비교해도 충분히 빠르다.
  • 결과가 반드시 재현 가능하고 설명 가능해야 하는 경우: ANN은 근사값이고, 왜 이 문서가 나왔는지 설명하기 어렵다.

실무에서는 키워드 검색과 벡터 검색을 함께 쓰는 하이브리드 검색이 흔하다. 이미 PostgreSQL을 쓰고 있다면 pgvector로 시작하고, 규모가 커질 때 전용 벡터 DB를 검토하는 순서가 부담이 적다. 임베딩 모델을 바꾸면 모든 벡터를 다시 만들어야 한다는 점도 기억해 두자.

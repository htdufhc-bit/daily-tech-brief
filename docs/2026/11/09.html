오늘의 기술

비동기 I/O와 이벤트 루프

커리큘럼 #28 운영체제 ⏱ 5분

비동기 I/O는 입출력이 끝나기를 기다리며 멈추지 않고 다른 일을 계속하게 해 주는 방식이고, 이벤트 루프는 준비된 I/O 이벤트를 하나씩 꺼내 처리하는 반복 구조다.

왜 필요한가

전통적인 방식은 연결 하나마다 스레드 하나를 두고, 데이터가 올 때까지 그 스레드를 블로킹한다. 연결이 수백 개일 때는 괜찮지만 수만 개가 되면 문제가 생긴다. 스레드마다 메모리(스택)가 필요하고, 스레드 사이를 오가는 컨텍스트 스위칭 비용도 커지기 때문이다. 게다가 대부분의 스레드는 네트워크나 디스크를 기다리며 CPU를 쓰지도 않고 자리만 차지한다.

비동기 I/O는 "기다리는 시간"을 다른 작업에 쓰자는 발상이다. 적은 수의 스레드(때로는 하나)로 많은 동시 연결을 처리할 수 있어서 웹 서버, 채팅 서버, 크롤러처럼 I/O 비중이 큰 프로그램에서 자원을 크게 아낀다. Node.js, Nginx, 파이썬 asyncio, 자바스크립트의 Promise가 모두 이 모델 위에 있다.

동작 원리

  1. 프로그램이 파일이나 소켓 같은 I/O 작업을 논블로킹으로 요청하고, 결과를 기다리지 않고 바로 다음 코드로 넘어간다.
  2. 운영체제의 이벤트 알림 기능(Linux의 epoll, macOS의 kqueue, Windows의 IOCP)에 "이 소켓들 중 준비된 것이 생기면 알려 달라"고 한꺼번에 등록한다.
  3. 이벤트 루프가 반복문을 돌며 알림을 기다린다. 준비된 I/O가 있으면 거기에 연결해 둔 콜백(또는 재개할 코루틴)을 큐에서 꺼내 실행한다.
  4. 콜백이나 코루틴은 짧게 실행되고 다시 루프로 돌아온다. 한 스레드가 수천 개의 연결을 번갈아 처리하는 셈이다.
  5. async/await 문법은 이 과정을 읽기 쉽게 감싼 것이다. await를 만나면 현재 함수가 일시 중단되고 제어권이 루프로 넘어가며, 결과가 준비되면 그 지점에서 다시 시작한다.

핵심 규칙은 루프를 막지 않는 것이다. 루프 안에서 오래 걸리는 계산이나 블로킹 호출을 하면 다른 모든 작업이 멈춘다.

예시

아래는 파이썬 asyncio로 세 개의 작업을 동시에 실행하는 예시다. 각 작업은 I/O를 기다리는 동안 await로 제어권을 넘긴다.

import asyncio
import time

async def fetch(name: str, delay: float) -> str:
    await asyncio.sleep(delay)  # 네트워크 대기를 흉내 낸다
    return f"{name} 완료 ({delay}초)"

async def main():
    start = time.perf_counter()
    results = await asyncio.gather(
        fetch("A", 1.0),
        fetch("B", 1.5),
        fetch("C", 0.5),
    )
    for r in results:
        print(r)
    print(f"총 {time.perf_counter() - start:.1f}초")

asyncio.run(main())

순서대로 실행하면 3초가 걸리지만, 세 작업이 대기 시간을 겹쳐 쓰므로 가장 긴 작업과 비슷한 약 1.5초에 끝난다. time.sleep(1)처럼 블로킹 함수를 쓰면 이 이점이 사라진다는 점도 직접 바꿔 실행해 보면 확인할 수 있다.

언제 쓰고 언제 안 쓰나

쓰면 좋은 경우 - 동시 연결이 많은 네트워크 서버(API 게이트웨이, 채팅, 스트리밍) - 여러 외부 API나 DB를 동시에 호출해야 하는 작업 - 대기 시간이 대부분이라 CPU는 한가한 프로그램

피해야 할 경우 - 이미지 처리, 암호화, 대규모 계산처럼 CPU를 오래 쓰는 작업. 이벤트 루프 하나가 막혀 전체가 느려지므로 별도 프로세스나 워커 스레드로 분리해야 한다. - 동시성이 거의 필요 없는 단순 스크립트. 코드 복잡도(콜백, 예외 처리, 디버깅)만 늘어난다. - 동기 라이브러리를 그대로 async 함수 안에서 호출하는 경우. 겉보기만 비동기이고 실제로는 루프를 막는다.

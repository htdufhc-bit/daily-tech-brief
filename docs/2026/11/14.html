오늘의 기술

복제와 샤딩

커리큘럼 #33 데이터베이스 ⏱ 6분

복제는 같은 데이터를 여러 서버에 복사해 두는 기법이고, 샤딩은 데이터를 여러 서버에 나누어 저장하는 기법이다.

왜 필요한가

데이터베이스 서버 한 대로 서비스를 운영하면 두 가지 문제가 생긴다.

  • 가용성: 서버가 죽으면 서비스 전체가 멈추고, 디스크가 망가지면 데이터를 잃을 수 있다.
  • 확장성: 요청이 늘면 서버 사양을 올리는 수직 확장에는 한계와 비용 문제가 있다.

복제는 읽기 부하를 분산하고 장애에 대비하기 위해, 샤딩은 데이터 양과 쓰기 부하가 한 대의 한계를 넘을 때 쓰려고 나왔다. 둘은 목적이 다르므로 자주 함께 쓰이지만 같은 개념이 아니다.

동작 원리

복제 (Replication)

  1. 쓰기는 주(primary) 서버가 받아 변경 내용을 로그(MySQL의 binlog, PostgreSQL의 WAL)에 기록한다.
  2. 복제본(replica) 서버가 이 로그를 받아 같은 순서로 적용한다.
  3. 읽기 요청은 복제본으로 보내 부하를 나눈다.
  4. 주 서버가 죽으면 복제본 하나를 새 주 서버로 승격(failover)한다.

복제에는 동기와 비동기 방식이 있다. 동기식은 복제본이 반영을 끝낼 때까지 기다리므로 데이터는 안전하지만 쓰기가 느려진다. 비동기식은 빠르지만 복제본이 잠깐 뒤처질 수 있어(복제 지연) 방금 쓴 값이 읽히지 않을 수 있다.

샤딩 (Sharding)

  1. 데이터를 나누는 기준인 샤드 키를 정한다. 예를 들어 사용자 ID.
  2. 키를 규칙에 따라 샤드에 대응시킨다. 대표적으로 범위 방식(ID 1~100만은 샤드 A), 해시 방식(해시(ID) % 샤드 수), 디렉터리 방식(매핑 표를 따로 둔다)이 있다.
  3. 애플리케이션이나 라우터가 키를 보고 알맞은 샤드로 요청을 보낸다.
  4. 각 샤드는 자기 몫의 데이터만 가지므로 쓰기와 저장 용량이 샤드 수만큼 늘어난다.

샤딩의 약점은 여러 샤드에 걸친 조인과 트랜잭션이 어렵다는 점과, 샤드를 늘릴 때 데이터를 다시 옮기는 리밸런싱이 필요하다는 점이다.

예시

해시 방식 샤딩에서 사용자 ID로 샤드를 고르는 파이썬 예시이다. 읽기는 복제본 중 하나로 보내고 쓰기는 주 서버로 보내는 구조를 함께 표현했다.

import random, zlib

# 샤드마다 주 서버 1대와 복제본 2대
SHARDS = [
    {"primary": "db0-primary", "replicas": ["db0-r1", "db0-r2"]},
    {"primary": "db1-primary", "replicas": ["db1-r1", "db1-r2"]},
]

def pick_shard(user_id: int) -> dict:
    # 파이썬 내장 hash()는 실행마다 달라질 수 있어 crc32를 쓴다
    h = zlib.crc32(str(user_id).encode())
    return SHARDS[h % len(SHARDS)]

def route(user_id: int, write: bool) -> str:
    shard = pick_shard(user_id)
    return shard["primary"] if write else random.choice(shard["replicas"])

print(route(42, write=True))   # 항상 해당 샤드의 주 서버
print(route(42, write=False))  # 해당 샤드의 복제본 중 하나

같은 user_id는 항상 같은 샤드로 가고, 읽기만 복제본으로 분산된다. 단, % len(SHARDS) 방식은 샤드 수가 바뀌면 대부분의 키가 다른 샤드로 옮겨지므로 실제 서비스에서는 일관된 해싱 같은 기법을 쓴다.

PostgreSQL에서 복제본을 읽기 전용으로 띄우는 설정은 다음과 같다.

# primary의 postgresql.conf
wal_level = replica
max_wal_senders = 5

# replica 쪽: 주 서버를 가리키는 접속 정보
primary_conninfo = 'host=db0-primary user=replicator password=...'

복제본 데이터 디렉터리에 standby.signal 파일을 만들고 서버를 시작하면 복제본으로 동작한다.

언제 쓰고 언제 안 쓰나

복제를 쓰면 좋은 경우

  • 읽기 요청이 쓰기보다 훨씬 많은 서비스 (게시판, 상품 조회)
  • 장애 시 빠른 복구가 필요한 서비스, 백업이나 분석용 쿼리를 따로 돌리고 싶을 때

샤딩을 쓰면 좋은 경우

  • 데이터가 한 서버의 디스크나 메모리에 담기지 않을 때
  • 쓰기 부하가 단일 주 서버의 한계를 넘을 때

피해야 할 경우

  • 아직 서버 한 대로 충분하다면 샤딩은 미루는 것이 좋다. 인덱스 정비, 쿼리 튜닝, 캐시, 읽기 복제본으로 먼저 해결할 수 있는지 확인한다.
  • 샤딩은 조인, 트랜잭션, 운영 복잡도를 크게 높이므로 샤드 키 선택을 신중히 해야 하고, 한 번 정하면 바꾸기 어렵다.
  • 복제 지연을 감안하지 않고 읽기를 복제본에 보내면 방금 저장한 데이터가 보이지 않는 문제가 생긴다.

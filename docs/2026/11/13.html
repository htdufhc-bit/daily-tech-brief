오늘의 기술

WebSocket

커리큘럼 #32 웹 ⏱ 5분

WebSocket은 하나의 TCP 연결 위에서 클라이언트와 서버가 언제든 서로 메시지를 주고받을 수 있게 하는 양방향 통신 프로토콜이다.

왜 필요한가

HTTP는 클라이언트가 요청해야만 서버가 응답하는 구조라, 채팅·주식 시세·협업 편집처럼 서버가 먼저 알려줘야 하는 기능을 만들기 불편하다. 이를 흉내 내려고 주기적으로 서버에 물어보는 폴링(polling)을 쓰면 변화가 없어도 요청이 계속 오가 낭비가 크고, 새 소식이 와도 다음 요청까지 지연된다. 롱 폴링은 지연을 줄이지만 요청마다 헤더를 다시 보내고 연결을 계속 맺고 끊어야 한다. WebSocket은 연결을 한 번 맺어 두고 작은 프레임만 주고받아 이 비용과 지연을 크게 줄이려고 나왔다.

동작 원리

  1. 핸드셰이크: 클라이언트가 일반 HTTP GET 요청에 Upgrade: websocket, Connection: Upgrade, Sec-WebSocket-Key 헤더를 실어 보낸다.
  2. 프로토콜 전환: 서버가 동의하면 101 Switching Protocols로 응답하고, 이후 같은 TCP 연결이 HTTP가 아닌 WebSocket 프레임을 주고받는 통로가 된다.
  3. 프레임 교환: 데이터는 작은 헤더가 붙은 프레임 단위로 오간다. 텍스트·바이너리 프레임과 함께 연결 상태를 점검하는 ping/pong, 종료를 알리는 close 프레임이 있다. 요청-응답 짝이 없으므로 양쪽이 언제든 먼저 보낼 수 있다.
  4. 종료: 한쪽이 close 프레임을 보내고 상대가 응답하면 TCP 연결이 정리된다. 네트워크가 끊기면 클라이언트가 재연결을 직접 구현해야 한다.

예시

브라우저에는 WebSocket API가 내장되어 있어 몇 줄이면 연결할 수 있다. 아래는 주소를 열고 메시지를 주고받는 클라이언트 코드다.

const ws = new WebSocket("wss://echo.example.com/chat");

ws.addEventListener("open", () => {
  ws.send("안녕하세요");
});

ws.addEventListener("message", (event) => {
  console.log("받음:", event.data);
});

ws.addEventListener("close", () => {
  console.log("연결 종료");
});

서버 쪽은 Node.js의 ws 라이브러리로 받은 메시지를 모든 접속자에게 뿌리는 간단한 채팅 서버를 만들 수 있다.

import { WebSocketServer, WebSocket } from "ws";

const wss = new WebSocketServer({ port: 8080 });

wss.on("connection", (socket) => {
  socket.on("message", (data) => {
    for (const client of wss.clients) {
      if (client.readyState === WebSocket.OPEN) {
        client.send(data.toString());
      }
    }
  });
});

운영 환경에서는 TLS를 적용한 wss://를 쓰는 것이 기본이다.

언제 쓰고 언제 안 쓰나

쓰면 좋은 경우: 채팅, 실시간 알림, 온라인 게임, 공동 문서 편집, 실시간 시세처럼 지연이 짧고 양방향 메시지가 잦은 서비스.

피해야 할 경우: 서버에서 클라이언트로만 보내면 충분한 단순 알림이라면 Server-Sent Events가 더 간단하다. 가끔 갱신되는 데이터는 일반 HTTP 요청이면 충분하다. 또한 연결이 계속 유지되므로 서버가 동시 접속 수만큼 자원을 쓰고, 로드밸런서·프록시의 유휴 연결 타임아웃, 재연결과 인증 처리, 여러 서버 간 메시지 전달(예: 메시지 브로커) 같은 운영 부담이 생긴다는 점을 고려해야 한다.
